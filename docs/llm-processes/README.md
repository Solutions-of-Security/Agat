## Создать процесс в интерфейсе

1. Откройте **Процессы → Новый процесс**. В поле «Источник процесса» выбран каталог типовых процессов.
2. Выберите категорию или найдите сценарий поиском. Выберите карточку; форма заполнит название и описание. Если имя занято, предложит независимую копию с суффиксом.
3. Просмотрите результат, вход, этапы и критерии приёмки. Назначьте существующих агентов на роли исполнителя и проверяющего. Можно оставить назначения на потом.
4. Нажмите **Создать процесс**. Откроется редактируемый черновик. Он содержит конкретные задания этапов, шаги агентов, решение человека и сохранение Markdown-артефакта.
5. Проверьте инструкции выбранных агентов, модель, доступ к источникам, инструменты и лимиты. Назначьте оставшиеся роли, подготовьте фактические входные данные, пройдите проверки графа и опубликуйте версию.
6. Запустите процесс, выбрав коллекции знаний при необходимости. После работы агентов примите или отклоните итоговый материал в согласованиях. Принятие разрешает сохранение результата, а не выполнение внешней операции.

Коллекции, credentials, расписания и webhooks не копируются из встроенного каталога. Роль в карточке — назначение в процессе, не новая роль RBAC и не автоматическая установка агента. Выбранный агент сохраняет собственный system prompt и права; задания этапов не отменяют эти настройки. Для независимой проверки можно назначить другого агента, но это не заменяет человеческое решение или four-eyes policy.

Для повторного использования своей схемы отметьте **Сохранить как шаблон**. В следующих процессах выберите **Источник процесса → Шаблон проекта**. Копируется последняя опубликованная версия, а при её отсутствии — черновик, в том числе с неназначенными агентами. Последующие изменения оригинала не меняют копию. Обновления шаблона переносятся вручную через редактор и review версии.

## Создать через API

`GET /api/v1/process-templates` возвращает категории, паспорта и графы. Используется обычная аутентификация Agat и чтение для существующих read-ролей. Каталог общий и не содержит частных агентов, credentials или документов.

`POST /api/v1/processes` доступен `admin`/`designer` и создаёт процесс в выбранном проекте (`x-agat-project-id`). Пример тела, создающий черновик без назначения агентов:

```json
{
  "name": "Еженедельное исследование",
  "description": "Отчёт по внутренним источникам",
  "catalogTemplateId": "research-to-report",
  "catalogTemplateVersion": 1,
  "templateBindings": {},
  "isTemplate": false
}
```

Для назначения добавьте в `templateBindings` пары «ID роли → ID существующего доступного агента». ID ролей берутся из `roles` выбранного шаблона. Например, у исследования это `researcher` и `reviewer`; имена агентов не используются как идентификаторы. Один исполнитель назначается на все этапы своей роли.

- Версия обязательна. При неизвестной/устаревшей версии запрос отклоняется: получите каталог заново и проверьте изменение.
- Нельзя одновременно передать `catalogTemplateId` и `graph`/`templateId`.
- Неизвестная роль, отсутствующий или чужой частный агент отклоняются до записи процесса. Встроенные агенты доступны согласно существующим правилам Agat.
- Каталог создаёт только draft: `publishedVersion=0`, запуск до публикации невозможен. Публикация выполняет строгую проверку графа, в том числе назначений агентов.
- В `process.created` записываются ID и версия исходного шаблона, категория. Отдельного хранилища старых версий каталога нет; созданный граф остаётся независимой сохранённой копией.
- Повторный POST не является идемпотентным API установки. Проверка уникальности имени внутри проекта остаётся прежней. После потери ответа сначала проверьте список процессов, а затем повторяйте создание при необходимости.

## Добавить собственный типовой процесс

Для локальной команды достаточно создать процесс из близкого шаблона, изменить задания/этапы, назначить ответственного и сохранить его как шаблон проекта. Заполните [паспорт](./templates/process-passport.md), а затем проверьте обычное выполнение, нехватку данных, ошибку исполнителя и отказ согласующего.

Для включения в поставляемый каталог:

1. Выберите одну основную категорию по конечному результату. Домен и схема исполнения описываются отдельно.
2. Добавьте определение в [process-catalog.ts](../../apps/coordinator/src/process-catalog.ts): уникальный ID, версия, роли, предметные этапы, вход, результат, критерии приёмки и исключения. При изменении поставляемого шаблона задайте увеличенную `version` в его определении и увеличьте версию каталога. Маркер версии артефакта строится автоматически.
3. Проверьте граф строгим валидатором с тестовыми назначениями. Проведите сценарии acceptance/rejection и убедитесь, что результат до согласования не выдан как финальный process artifact.
4. Перегенерируйте документы и проверьте синхронность:

```bash
npm run docs:processes
npm run docs:processes:check
node --import tsx --test apps/coordinator/test/process-catalog.test.ts apps/web/test/process-templates.test.ts
npm run typecheck
```

Канонический источник — TypeScript-каталог в coordinator. [JSON](./catalog.json) и [Markdown](./catalog.md) генерируются скриптом [export-process-catalog.ts](../../scripts/export-process-catalog.ts); их не следует править отдельно. Для схем, выходящих за линейную подготовку и review, добавьте специализированный построитель графа и тесты ветвления/сбоя. Не добавляйте декоративные шаги, обещающие отсутствующую интеграцию.

## Граница готовности

Эта поставка закрывает **каталог и быстрое создание схем подготовки/согласования**. Она не означает завершение roadmap packs `SP-102`–`SP-302`: для production нужны реальные источники, доменные схемы/валидаторы, коннекторы, ограничение прав инструментов, квалификация модели, eval и решение владельца процесса. В частности, данный каталог не исполняет платежи, подписание, Git/CI release, изменение инфраструктуры или доступов. Нужные продолжения описаны в каждом паспорте.
