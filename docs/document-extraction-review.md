# Проверка извлечённого текста документов

USE-003 / UX-206, 25 октября 2026. Успешный разбор PDF/DOCX ещё не означает,
что документ целиком доступен модели. Файл сначала получает состояние
`review_required`; индексация и выдача model lease с этой коллекцией ожидают
явного решения администратора или проектировщика проекта.

## Что показывает проверка

Отчёт `document-extraction.v1` сохраняет профиль парсера, число извлечённых
UTF-16 символов, доступные page metadata, страницы PDF без текста,
имена дополнительных текстовых частей DOCX и обнаруженные особенности XML.
`fidelity: not_assessed` сохраняется и после решения человека.

| Формат / профиль | Доступный материал | Ограничения |
| --- | --- | --- |
| PDF / `pdf-text-layer.v1` | Текстовый слой и физические номера страниц | Нет OCR, проверки изображений, таблиц и визуального расположения. Страница без текста может быть пустой или содержать скан |
| DOCX / `docx-main-document.v1` | Текст `word/document.xml`, абзацы и линейный текст таблиц | Header/footer, footnotes/endnotes, comments и glossary перечисляются как отдельные пропущенные части. Изображения, поля, tracked changes, math и таблицы помечаются при обнаружении. Номера страниц не назначаются |
| CSV / `csv-values.v1` | Текстовые значения и адреса логических ячеек | Ограничения [табличного разбора](./tabular-knowledge-ingest.md) |
| XLSX / `xlsx-values.v1` | Хранимые значения ячеек | Формулы и макросы отклоняются; графики, изображения, даты и оформление не интерпретируются |
| Текст / `provided-text.v1` | Переданный текст | Исходная визуальная форма не оценивается |

PDF/DOCX требуют решения при любом успешном разборе. Отсутствие обнаруженных
особенностей не доказывает полноту. CSV/XLSX и переданный текст индексируются
автоматически в пределах явно указанного профиля. Ошибочный или пустой разбор
имеет `unavailable` / `failed`; подтвердить его вместо исправления нельзя.
Сохраняются прежние лимиты размера, времени, памяти и изоляция parser worker.
DOCX дополнительно ограничен 2000 ZIP-записями и 100 дополнительными частями.

## Решение и повторный разбор

1. Открыть Knowledge → документ, скачать оригинал и сверить его с предпросмотром.
2. Проверить страницы без текста и части, не вошедшие в разбор. При нехватке
   данных подготовить подходящий исходник; встроенного OCR на этом этапе нет.
3. Явно отметить использование **только извлечённого текста**, указать причину
   и нажать «Подтвердить текст и индексировать». Checkbox изначально выключен.
4. Дождаться готовности embeddings. Подтверждение текста не означает готового
   индекса, успешного отчёта, истинности данных или бизнес-приёмки.

`POST /api/v1/knowledge/documents/:id/review-extraction` принимает только:

```json
{
  "originalSha256": "<SHA-256 оригинала>",
  "contentSha256": "<SHA-256 извлечённого текста>",
  "reportSha256": "<SHA-256 JSON отчёта разбора>",
  "extractionRevision": "<UUID текущего разбора>",
  "decision": "use_extracted_text_only",
  "reason": "<непустая причина, до 1000 символов>"
}
```

SHA-256 отчёта вычисляется по сохранённому JSON; клиент передаёт возвращённый
сервером digest. Три hashes и revision должны совпасть с текущим документом.
Actor берётся из аутентифицированного subject. Сохраняются решение, причина,
actor и время. Audit event содержит hashes, revision и hash причины без её текста.
Tenant/project scope и `admin/designer` проверяются сервером.

Подтверждение сериализуется блокировкой коллекции и строки документа.
Review/reindex сохраняют порядок collection → existing job → document,
совместимый с завершением embeddings. Повтор того же
запроса возвращает существующую квитанцию и не создаёт новую embedding job
или audit event. Повторный разбор сбрасывает квитанцию, отзывает старые leases
и всегда получает новую UUID revision, даже если bytes и текст совпали.
Старая форма не может подтвердить новую ревизию. Переиндексация во время
активного run по-прежнему запрещена; подтверждение неизменного текста может
разблокировать ожидающий run.

## До модели и после результата

Preflight показывает точную причину и ссылку на Knowledge. Выдача agent lease,
включая обычный run без process graph, блокируется при неизвестном, ошибочном
или ожидающем проверки файловом разборе в выбранной коллекции. Файлы без
принятого scope не входят в retrieval.

Сохранённый source provenance содержит профиль, report hash, revision,
review hash/decision, известные gap counts, features и `not_assessed`.
Неприменимые или неизвестные counts остаются `null`, а не превращаются в ноль.
Worker получает ограничения вместе с контекстом. Markdown-источники и UI export
сохраняют предупреждение о непроверенной визуальной полноте.
Выходной business contract повторно сверяет источник и текущую квитанцию:
изменившийся разбор не подходит для нового проверяемого артефакта.
Исторические retrieval snapshots сохраняются для проверки завершённых runs.

## Обновление хранилища

Schema **32**, contract `agat-document-extraction-review-v32`, добавляет четыре
колонки к `knowledge_documents`: state, report JSON, review JSON, revision.
PostgreSQL обновляется отдельной migration/admission Job при остановленных
coordinators; runtime остаётся DDL-free. [Процедура](./postgresql-migration-job-runtime-role.md).

Ранее загруженные файлы без отчёта становятся `legacy_unknown` /
`review_required`. Их embedding jobs отзываются, исходные bytes, извлечённый
текст, chunks и исторические sources сохраняются. Перед дальнейшим использованием
нужен текущий повторный разбор и применимое решение человека. Старые текстовые
документы сохраняют совместимость. Offline SQLite → PostgreSQL переносит report,
revision и квитанцию вместе с остальными данными и сверяет canonical digests.

## Основание и проверки

PDF.js [`getTextContent`](https://mozilla.github.io/pdf.js/api/draft/api.js.html)
возвращает текстовый слой страницы. Различие текста, изображений и OCR описано
в [pypdf](https://pypdf.readthedocs.io/en/latest/user/extract-text.html).
WordprocessingML состоит из нескольких stories/parts, а не одного main body:
[Microsoft Open XML](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document).
Поэтому выбран явный scope с решением человека; автоматическое утверждение
полноты из числа символов или отсутствия пустых страниц недостоверно.

Проверки используют синтетические документы:

- parser: смешанный PDF с пустой физической страницей, DOCX с omitted stories/features;
- store/HTTP: отказ до review, hashes/reason/project/role checks, idempotence,
  restart, одинаковые bytes при новой revision, legacy migration, provenance;
- настоящий PostgreSQL и две coordinator replicas: четыре одновременных review,
  одна job/event, foreign project denial, stale revision rejection;
- принудительные PostgreSQL barriers: review против reindex и embedding complete
  против reindex; новое извлечение не наследует job, stale reindex не стирает
  принятый текст и не создаёт deadlock;
- offline SQLite → PostgreSQL apply/verify и rehearsal rollback;
- desktop/mobile Chromium: загрузка, пустая страница, точные original bytes,
  выключенный checkbox, обязательная причина, подтверждение, reload и сброс
  формы после reindex. Browser plugin недоступен, использован Playwright;
- worker: ограничения сохраняются в RAG context, неизвестные counts не исчезают.

Это технические проверки границ. Проверка разрешённого пользовательского корпуса,
визуальная сверка реальных документов и квалификация роли/модели остаются
отдельными этапами плана.
