# Сравнение кандидатов на утверждённой development-разметке

26.09.2026, локальный runtime **0.3.0**. Реализован следующий блок [плана](../../../local-decision-model-plan-2026-09-21.md): перенос утверждённой ассистентом разметки в development-набор, одинаковая проверка кандидатов и разбор ошибок по исходным logits. Статус результата — **`diagnostic_only`**. Экспертная квалификация, обучение и автоматическая маршрутизация не выполнены.

В исходном порядке decider правильно выбрал **14/15** меток, базовый Qwen — **7/15**. Однако после перестановки вариантов decider принял одно ошибочное решение. Поэтому результат позволяет продолжать исследование кандидата, но не подтверждает готовность автоматических действий.

## Данные и границы проверки

Источник — [24 задания корпуса v2](../source-review/README.md), [утверждённые метки](../source-review/approved-labels.v2.json) и [ревью](../source-review/research-review.v2.json). Разметка сохраняет `labelSource: assistant-reviewed`. Это не две независимые человеческие рецензии.

Первоначальный seed `agat-source-review-2026-09-26-v1` взят из неизменённого пакета разметки. Он распределяет **15 случаев из двух групп в development**, девять случаев из трёх групп в holdout, ни одной группы в calibration. Экспорт содержит только development-запросы и ответы. Для отложенных случаев записаны исключительно ID, группа и split; они не передавались моделям.

Development содержит 4 проверки утверждений, 6 классификаций и 5 проверок достаточности данных. Реальных исходных заявок в нём две; остальные задания сформулированы по существующим документам. Примеров класса `access` нет. Два связанных источниковых кластера не позволяют оценить производственную частоту ошибок; 60 вычислений двух моделей в двух порядках остаются проверкой 15 зависимых случаев.

## Реализованные команды

`prepare-development` проверяет соответствие pool, утверждения и source review, хеши конкретных входов и схем, все метки и объяснения, отсутствие открытых замечаний, исходный blank-пакет с seed. SHA исходного ревью должен совпасть с утверждением; SHA pool и blank-пакета — с привязками в ревью. Остальные снимки источников проверяются отдельным `source-review/build.py --revision v2 --check`.

Проверка утечек выполняется на полном pool до исключения отложенных примеров: один источник или одинаковый нормализованный текст не может оказаться в разных splits. Новый набор получает `usage: development-only` и контрольную сумму. Попытки использовать его в `freeze`, назначить calibration/holdout или выдать разметку за экспертную отклоняются. SHA подтверждает целостность локальных файлов, а не подлинность личности рецензента.

`compare-development` принимает минимум два отчёта разных кандидатов для одного dataset, development split и одной policy. Оба порядка вариантов обязательны. Команда сверяет входы, модели, параметры policy и сырые некалиброванные logits, затем заново рассчитывает типизированные результаты и метрики. Сохранённые поля `correct`, `selectedOptionId`, probabilities и aggregate metrics не считаются эталоном. Ошибки backend остаются в знаменателе; строки разных семейств и ошибки перестановок видны отдельно. Парные счётчики сравнивают одни и те же case IDs независимо от порядка строк в файлах.

Отчёт содержит матрицы ошибок, покрытие меток, семейные метрики, группы с ошибочными принятыми решениями, расхождения порядка и ID проблемных случаев. Полные тексты запросов в него не копируются. Измеренная latency переносится из score reports; пересчёт logits не выдаётся за новое измерение inference. Команда не меняет пороги, не обучает температуру и не выбирает автоматически победителя.

Обе новые команды работают на стандартном Python без MLX. Модель нужна только для `evaluate`. Файлы создаются исключительно по новым путям. При корректной диагностике exit code — **0**, при ошибке входа — **1**; наличие backend errors тоже даёт **1**, но полный диагностический отчёт сохраняется. Низкое качество меток отражается в метриках и не превращает development-сравнение в квалификационный `pass`.

## Воспроизведение

Из корня проекта; для каждого нового прогона выберите новый каталог вместо `new-run`:

```bash
python3 docs/qualification/local-decisions/source-review/build.py --revision v2 --check

python3 -m decision_runtime prepare-development \
  --pool docs/qualification/local-decisions/source-review/pool.v2.json \
  --approval docs/qualification/local-decisions/source-review/approved-labels.v2.json \
  --review docs/qualification/local-decisions/source-review/research-review.v2.json \
  --split-reference docs/qualification/local-decisions/source-review/review.first.blank.v2.json \
  --output docs/qualification/local-decisions/development/evidence/new-run/dataset.json

.venv/decision/bin/python -m decision_runtime evaluate \
  --manifest .local-models/decisions/decider-2b.json \
  --dataset docs/qualification/local-decisions/development/evidence/new-run/dataset.json \
  --split development --reverse-options \
  --output docs/qualification/local-decisions/development/evidence/new-run/decider-scores.json

.venv/decision/bin/python -m decision_runtime evaluate \
  --manifest .local-models/decisions/qwen3.5-2b-base.json \
  --dataset docs/qualification/local-decisions/development/evidence/new-run/dataset.json \
  --split development --reverse-options \
  --output docs/qualification/local-decisions/development/evidence/new-run/qwen-base-scores.json

python3 -m decision_runtime compare-development \
  --dataset docs/qualification/local-decisions/development/evidence/new-run/dataset.json \
  --scores docs/qualification/local-decisions/development/evidence/new-run/decider-scores.json \
           docs/qualification/local-decisions/development/evidence/new-run/qwen-base-scores.json \
  --output docs/qualification/local-decisions/development/evidence/new-run/comparison.json
```

## Результат реального прогона

Сохранены [development-набор](./evidence/2026-09-26/dataset.json), [decider scores](./evidence/2026-09-26/decider-scores.json), [Qwen scores](./evidence/2026-09-26/qwen-base-scores.json) и [сравнение](./evidence/2026-09-26/comparison.json). Все 60 вычислений выполнены локально без ошибок backend. У обоих кандидатов одинаковые prompt, runtime fingerprint, лимит 2048 токенов, MLX 0.32.2 / mlx-lm 0.31.3, неквантованные веса и температура 1.0. Policy не менялась: вероятность ≥ 0.8, margin ≥ 0.1; семантический вариант abstain сохраняется независимо от вероятности.

| Метрика | decider, исходный порядок | decider, обратный | Qwen Base, исходный | Qwen Base, обратный |
|---|---:|---:|---:|---:|
| Верные метки | 14/15 | 14/15 | 7/15 | 7/15 |
| Принятые решения | 8/15 | 10/15 | 2/15 | 3/15 |
| Ошибки среди принятых | 0/8 | **1/10** | **1/2** | **2/3** |
| Macro-F1 по классам с определённым F1 | 0.9405 | 0.9500 | 0.4333 | 0.3292 |
| NLL | 0.2313 | 0.2622 | 1.0425 | 1.2222 |
| Brier | 0.1281 | 0.1511 | 0.6256 | 0.7288 |
| ECE10 | 0.1309 | 0.1487 | 0.1760 | 0.2957 |
| p95 вычисления, мс | 537.295 | 277.022 | 943.736 | 267.962 |

Метка сохранилась при перестановке у decider в **13/15** случаев, у Qwen — **4/15**. Это сравнение двух закреплённых checkpoints одним адаптером; не сравнение со всеми возможными способами prompt/scoring базовой модели. Малое число наблюдений, зависимые источники, отсутствие access-примеров и человеческого gold ограничивают выводы. Нулевые ошибки в исходном порядке decider не компенсируют ошибку другого порядка.

p95 в таблице включает первое вычисление; при 15 исходных случаях это максимум. Загрузка модели учитывается отдельно в `timing.modelLoadMs`, HTTP и очередь в эти измерения не входят. Это локальный диагностический замер, не производственный SLO или проверка под нагрузкой.

Машина прогона — **Apple M1 Max, 32 ГиБ unified memory**. Входы содержали 152–591 токен. Загрузка decider/Qwen заняла 7184.638/5805.465 мс; p95 следующих исходных запросов — 307.554/304.481 мс. Пиковые выделения MLX — 4 194 116 850 и 4 223 133 340 байт; это счётчик MLX, а не полный RSS процесса. Модели запускались последовательно, без конкурентной нагрузки.

## Разбор ошибок и дальнейшая работа

| Случай | Наблюдение | Следствие |
|---|---|---|
| `agat-source-019` | decider запросил лишние сведения для незаполненного шаблона, но остановился по порогу; при обратном порядке дал правильный `sufficient` | На development проверить устойчивость различия между подготовкой шаблона и проведением исследования |
| `agat-source-021` | Для начала пилота не заданы команды, владелец и baseline. При обратном порядке decider выдал ошибочное `sufficient` с p=0.8176 и `ok` | Ошибка смысла и чувствительность к порядку; температура сама по себе правильную метку не восстановит |
| `agat-source-015` | Qwen Base принял `enhancement` для зафиксированного инцидента, p=0.8384 | Прямой scorer базовой модели на этом входе не удерживает границу категории |
| `agat-source-009`, `agat-source-019` | В обратном порядке Qwen принял ошибочную категорию заявки и лишнее уточнение | Проверять исходный и обратный порядок необходимо и при низком общем покрытии |

Тексты и rationale сохранены в development-наборе, исходные доказательства — в неизменённом пакете source-review v2. Все ошибки находятся также в `models[].diagnostics` машинного сравнения. Пороги и утверждённые метки после просмотра ответов не редактировались.

Следующие зависимости плана остаются открытыми:

1. Собрать новые независимые источники и реальные заявки, включая доступы; обеспечить calibration split с нужными схемами. Уже выбранный seed не подбирать по результатам.
2. Выполнить два независимых человеческих review и заранее закрепить предметные критерии. Нынешние assistant-метки автоматически не повышаются до `expert-reviewed`.
3. На development разобрать ошибки достаточности данных и порядок кандидатов; после расширения данных сравнить альтернативу или дообучение с decider и с правилами/текущей генеративной проверкой на тех же входах. В этом прогоне сравнивались только два direct-logit checkpoint.
4. После фиксации кандидата выполнить новую calibration и независимую qualification. Старый синтетический fit v0.2.0 не переносится на новые схемы и исходники runtime.
5. Подключить worker capability/profile, проверку coordinator и fallback сначала в shadow. Это отдельный инженерный этап; в текущем изменении worker leases и маршрутизация процессов не подключены.

## Проверки

`npm run test:decision` включает тесты экспорта, защиты от утечек, подмены approved-меток/seed/review, повторной записи файлов, ошибок backend, порядка строк/вариантов и пересчёта недостоверных aggregate metrics. Исторические calibration/qualification v0.2.0 перепроверены по сохранённым logits: температура, метрики и gates совпали с прежними отчётами.

Финально в Python 3.13 прошло **63 теста**, включая **19 новых**; три opt-in GPU-теста пропущены в стандартном запуске. Две реальные GPU/HTTP-проверки выполнены отдельно и прошли. Исторический calibrated HTTP-тест не запускался с несовместимым fit v0.2.0. `npm run docs:check` прошёл: 12 Node-тестов, два Python-теста, 834 локальные ссылки в 114 Markdown-файлах и каталог процессов. Оба пакета source-review v1/v2 воспроизводятся; `git diff --check` не обнаружил ошибок.

Проверки актуального runtime и корпуса фиксируются в [протоколе](./evidence/2026-09-26/verification.json); отдельные реальные [GPU-проверка головы и изоляции](./evidence/2026-09-26/runtime-check.json) и [HTTP-вызов](./evidence/2026-09-26/runtime-check-http.json) также сохранены.
