# Генеративный baseline на тех же development-входах

26.09.2026. Добавлен локальный label-based baseline `qwen3:8b` и проверяемое сравнение с ранее измеренными decider/Qwen Base. Результат — **`diagnostic_only`**, обучение и автоматическая маршрутизация не включены.

Используются те же 15 случаев из [утверждённого development-экспорта](../development/evidence/2026-09-26/dataset.json), два источниковых кластера и исходные метки `assistant-reviewed`. Девять отложенных случаев в этот набор не входят. Для каждого входа выполнены исходный и обратный порядок вариантов, всего 30 реальных генераций.

## Результат

| Кандидат и режим | Верные метки, исходный порядок | Верные метки, обратный порядок | Случаи со сменой метки |
|---|---:|---:|---:|
| decider-2b, logits | 14/15 | 14/15 | 2 |
| Qwen3 8B Q4_K_M, JSON generation | 9/15 | 8/15 | 1 |
| Qwen3.5 2B Base, logits | 7/15 | 7/15 | 11 |

Машинные свидетельства: [генеративные результаты](./evidence/2026-09-26/qwen3-generative.json), [проверенное сравнение](./evidence/2026-09-26/comparison-verified.json). Сравнение заново проверяет привязки входов/меток и пересчитывает logits-результаты; ранее сохранённые aggregate metrics не используются как эталон. SHA исходников анализа сохранён отдельно от SHA реализации генератора.

У Qwen3 основные ошибки: утверждение о причине сбоя (`007`), различение дефекта и нового поведения (`009`, `011`, `012`), наличие конкретных значений в roadmap (`021`). В `023` и `024` генератор отказался выбирать вариант, хотя эталонная метка — `needs_clarification`. Эти отказы остаются в знаменателе accuracy. Смена порядка изменила Qwen3-метку для `011`.

У decider сохраняется известная проблема `021`: после перестановки вариантов ошибочный ответ проходит экспериментальные пороги. Поэтому даже лучший результат этого небольшого сравнения не разрешает автоматические действия. Замена decider на более крупный Qwen3 с данным prompt/режимом не устраняет выявленные ошибки; дальнейшее обучение пока не обосновано достаточными независимыми данными.

## Что именно сравнивалось

Генератор: установленный локально `qwen3:8b`, 8.2B, Q4_K_M, Ollama **0.34.2**, digest `500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41`. Это тот же модельный артефакт, который использовался в [пакете внутреннего отчёта](../../internal-report/results.md); новый тест использует отдельный классификационный prompt, а не три этапа отчётного workflow. Версия Ollama в прежнем прогоне была 0.34.0.

Параметры фиксированы до вычислений: `temperature=0`, `seed=0`, `think=false`, `num_ctx=8192`, `num_predict=128`. Низкая температура уменьшает случайность, но не доказывает побитовую воспроизводимость разных версий runtime/железа. Входы, вопросы и варианты сохраняются; модель не получает gold, rationale, группы или результаты decider.

JSON schema разрешает только `selectedOptionId`: ID одного из вариантов либо `null`. Код проверяет результат, получает Boolean из выбранного ID и различает `false`, abstain и ошибку. Неизвестный ID, дополнительные поля, повтор JSON-ключа, незавершённая генерация и неожиданные tool/thinking-ответы считаются ошибками. `null` — самостоятельный отказ от выбора; опция с `abstain: true` сохраняет свою метку, но не принимается как автоматическое решение.

Текстовые confidence/probability не запрашиваются и не интерпретируются. У генеративного baseline нет NLL/Brier/ECE и вероятностного порога. Его `ok` означает валидную декодированную метку, а у logits-профиля — прохождение policy. Поэтому coverage и selective risk в машинном отчёте имеют разные правила принятия и не являются сравнением при одинаковом допустимом риске. Общее label accuracy сравнивается на одних и тех же входах.

Исходный p50/p95 Qwen3 — 1464.743/5873.317 мс, обратный — 1474.264/2033.128 мс. Первый запрос включает прогрев. Latency decider и Qwen Base взята из прежних отчётов; разные размеры, квантование, runtime, состояние cache и время запуска не позволяют объявить эти числа контролируемым performance benchmark.

## Инструменты и воспроизведение

Код: [CLI](../../../../scripts/evaluate-decision-baselines.py), [адаптер и сравнение](../../../../scripts/lib/decision_baselines.py), [тесты](../../../../scripts/test/test_decision_baselines.py). Работают на стандартном Python; новые пакеты и модельные веса не требуются, если Qwen3 уже установлен.

Команды выполняются из корня репозитория. Сервер Ollama должен быть локальным; инструмент принимает только буквальный `127.0.0.1`, не использует proxy и redirects. Наличие модели и cloud/proxy-признаки проверяются до отправки данных; digest перепроверяется перед каждым inference. Автоматической загрузки модели нет.

```bash
python3 scripts/evaluate-decision-baselines.py evaluate \
  --url http://127.0.0.1:11434 \
  --model qwen3:8b \
  --expected-digest 500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41 \
  --dataset docs/qualification/local-decisions/development/evidence/2026-09-26/dataset.json \
  --output docs/qualification/local-decisions/baselines/evidence/new-run/qwen3-generative.json

python3 scripts/evaluate-decision-baselines.py compare \
  --dataset docs/qualification/local-decisions/development/evidence/2026-09-26/dataset.json \
  --generative docs/qualification/local-decisions/baselines/evidence/new-run/qwen3-generative.json \
  --logits docs/qualification/local-decisions/development/evidence/2026-09-26/decider-scores.json \
           docs/qualification/local-decisions/development/evidence/2026-09-26/qwen-base-scores.json \
  --output docs/qualification/local-decisions/baselines/evidence/new-run/comparison.json

python3 -m unittest discover -s scripts/test -p test_decision_baselines.py
```

CLI требует sealed dataset с `usage: development-only`; calibration/holdout отклоняются до inference. Контекст ограничивается консервативным бюджетом UTF-8 для подготовленного запроса с запасом на prompt/template/output; длинные входы получают `context_bound_exceeded`. В этом прогоне все запросы укладывались: 1304–3431 байт до системной обёртки. Сетевой deadline и размер ответа ограничены; сообщения/исключения модели не попадают в отчёт. Сохраняются выбранный ID, типизированное значение, токены, длительность и SHA исходного JSON-ответа.

Файлы не перезаписываются. Низкая точность даёт корректный диагностический отчёт; ошибки backend сохраняются и приводят к ненулевому exit code. Отсутствующий holdout, human reviews и права на маршрутизацию не заменяются успешным exit code.

## Источники и дальнейший шаг

[Документация Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs) описывает JSON schema, повтор схемы в prompt и снижение температуры. [Контракт Chat API](https://docs.ollama.com/api/chat) определяет отключение streaming/thinking, причину завершения и token usage. Реализация использует эти возможности для проверяемого выбора ID; схематически корректный JSON сам по себе не подтверждает правильность решения.

[Baseline по явному заголовку заявки](./rules.md) проверен: 2/15 правильных меток, только 1/15 принято. Его покрытие недостаточно; развитие по увиденным меткам остановлено. [Арифметический baseline](../performance/arithmetic.md) теперь вычисляет показатели из двух явных записей. Открыты mappings реальных источников, расширение независимых development/calibration-групп, отсутствующий класс `access` и два человеческих review. Порог decider, исходные метки и split seed по результатам этого сравнения не менялись. Следующее предметное сравнение должно включать новые независимые источники до решения о fine-tuning.

На [отдельных синтетических длинных входах](../performance/robustness.md#сравнение-с-генеративным-qwen3) Qwen3 также последовал вложенной команде во всех 18 вариантах. Сравнение сохраняет публичные поля задачи и использует непрозрачные ID; это диагностика, не qualification.
