# Продолжительная локальная HTTP-нагрузка

26.09.2026, runtime `0.9.0`. Дополнение к [коротким нагрузочным измерениям](./README.md): один постоянно работающий HTTP-сервер, последовательные запросы, показатели по временным окнам и RSS явно выбранных процессов. Проверяются доступность, неизменность профиля/ответов и изменение задержек во времени.

## Метод

Используется настоящий `LocalDecisionClient` и прежние 15 approved development-входов. В каждый запрос передаётся закреплённый SHA профиля. Валидатор проверяет привязку входа, logits/softmax, typed outcome, policy и токены. Для повторяющегося входа сравниваются точные SHA результата без duration: status, reason, value, selected option и distribution. Отчёт содержит fingerprints, но не копирует исходные тексты или gold labels.

После трёх прогревов начинается отдельный измерительный интервал. Новый запрос отправляется после завершения предыдущего, без очереди, retry или автоматического рестарта. При первой ошибке, смене решения, профиля или исчезновении наблюдаемого процесса прогон останавливается с `degraded` и сохраняет уже выполненные попытки. Ограничение числа запросов даёт `limited`; только полный заданный интервал без этих отказов даёт `observed`. Ни один статус не означает qualification модели.

Временные окна сохраняют latency вычисленных и отказов отдельно, количество запросов и throughput. Между окнами выполняются health-проверка и `ps` для указанных PID. Сравниваются PID, parent PID и время запуска, чтобы не принять другой процесс за исходный. RSS каждого процесса сохраняется отдельно: это resident memory по ОС, а не MLX active/cache, не Metal working set и не суммарная память устройства. Складывать его с MLX-счётчиками или RSS другого процесса нельзя. Краткие пики между снимками не измерены.

В [руководстве Grafana k6](https://grafana.com/docs/k6/latest/testing-guides/test-types/soak-testing/) полноценные soak tests обычно продолжаются часами и требуют наблюдения за ресурсами. Здесь выбран ограниченный локальный этап после smoke и краткой нагрузки; десять минут не заменяют многочасовую производственную проверку. Основной генератор, coordinator, другие пользователи и заданный поток входящих запросов в этом опыте отсутствуют.

## Воспроизведение

Запустите отдельный runtime с уже загруженными весами:

```bash
.venv/decision/bin/python -m decision_runtime serve \
  --manifest .local-models/decisions/decider-2b.json \
  --policy docs/qualification/local-decisions/policy.shadow.v1.json \
  --max-tokens 2048 --cache-limit-mib 128 --inference-timeout-ms 2000 \
  --port 8766
```

Определите PID именно этого сервера и его inference-процесса. Передайте их как повторяющийся `--process-pid`; без него ресурсные измерения не выполняются. Значения PID не входят в воспроизводимые константы. После проверки остановите только собственный временный сервер.

```bash
python3 scripts/benchmark-decision-endurance.py \
  --url http://127.0.0.1:8766 \
  --dataset docs/qualification/local-decisions/development/evidence/2026-09-26/dataset.json \
  --duration-s 600 --window-s 30 --max-requests 5000 --warmup 3 \
  --timeout-ms 10000 \
  --output docs/qualification/local-decisions/performance/evidence/new-run/endurance.json
```

Инструмент ограничен 1800 секундами, 10 000 запросами и 100 development-входами Choice/Boolean. Holdout, Score и некорректные лимиты отклоняются до сети. Время проверяется между запросами; каждый HTTP-вызов ограничен отдельно. Существующие evidence-файлы не перезаписываются. Эти пределы ограничивают эксперимент, а не утверждают допустимые настройки production.

Шесть автоматических тестов покрывают временные окна, предел запросов, остановку при ошибке/изменении профиля/ответа, неуспешный прогрев, запрет закрытых данных, отсутствие исходного текста/gold в отчёте, единицы RSS и обнаружение повторного использования PID. Они входят в `npm run docs:check`.

## Результат 26.09.2026

[600-секундный прогон](./evidence/2026-09-26/decider-endurance-600s.json) на Apple M1 Max / 32 ГиБ выполнил **3086 запросов** после трёх прогревов. Runtime 0.9.0: cache 128 МиБ, максимум 2048 токенов, изолированный inference с deadline 2000 мс. Входы содержали 152–591 токен; policy `agat.shadow.v1`, температура 1.

| Показатель | Наблюдение |
|---|---:|
| Полный измерительный интервал | 600.018 с |
| Выполнено / ошибок | 3086 / 0 |
| `ok` / `abstain` | 1646 / 1440 |
| HTTP p50 / p95 / max | 190.149 / 289.099 / 320.881 мс |
| Runtime p95 | 285.338 мс |
| Выполненных запросов в секунду | 5.143 |
| Временных окон / health+RSS снимков | 20 / 21 |
| Различий решения на одинаковом входе | 0 |

Первые окна имели p95 примерно 285–291 мс, последние — до **303.241 мс**. Причина позднего роста не изолирована; во время прогона на машине продолжались редактирование документации и небольшие CPU fixture-тесты. Другие модели намеренно не запускались. Сравнение с отдельными старыми прогонами не доказывает ускорения версии runtime.

RSS процесса HTTP-сервера: 22 446 080 байт после прогрева, 22 544 384 в конце, максимум снимков 22 790 144. RSS inference-процесса: 534 757 376 байт после прогрева, 489 963 520 в конце, максимум 536 887 296. Устойчивого роста этих наблюдаемых значений нет. Это не оценка полной памяти модели на Metal: ранее измеренные MLX active/cache остаются [отдельными величинами](./resources.md).

[Перепроверка](./evidence/2026-09-26/endurance-verification.json) проверила seal, SHA инструментов, все input fingerprints, последовательность вызовов, неизменность 15 decision signatures, summary каждого окна и p95 по исходным строкам. Профиль и идентичность двух процессов сохранились. После прогона сервер, inference-процесс и resource tracker остановлены; отсутствие PID проверено ОС. Качество, многочасовая стабильность и производственные SLO этим результатом не квалифицированы.
