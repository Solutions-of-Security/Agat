# Полнота кандидатов и точность topK локального поиска

26.09.2026. Исправлено поведение большой коллекции: **при превышении 5000 готовых кандидатов на query coordinator отклоняет поиск**, сохраняя ограничение ресурсов. Прежняя реализация брала 5000 самых свежих фрагментов, ранжировала только их и возвращала обычный успешный ответ. Старый источник с точным совпадением мог отсутствовать в таком ответе.

## Воспроизведение

[Сохранённый диагностический скрипт](./evidence/2026-09-26/retrieval-capacity/agat-rag-cap-probe.ts) создал временную SQLite и проиндексировал документы через обычные методы ingestion, embedding lease и completion. Векторы явно синтетические, двумерные: старый целевой фрагмент `[1, 0]`, более новые фрагменты `[0, 1]`, query `[1, 0]`. Для однозначного порядка целевому фрагменту задана старая дата индексации. Модель и внешние источники не использовались.

| Готовых фрагментов | Результат до исправления | Score |
|---:|---|---:|
| 5000 | Целевой старый фрагмент найден | 1 |
| 5001 | Целевой фрагмент выпал, возвращён ортогональный | 0 |

[Исходный результат](./evidence/2026-09-26/retrieval-capacity/agat-rag-cap-probe.json) включает 159 embedding batches с fixture-векторами и два времени исполнения. Два замера не являются нагрузочным benchmark или SLO. Смысл проверки — потеря известного кандидата на границе лимита. Скрипт закрепляет именно прежнее поведение и не является текущей командой проверки после исправления.

## Изменение

[SQL-поиск](../../../../apps/coordinator/src/database.ts) читает максимум 5001 строку в одном запросе и проверяет предел до ранжирования и записи retrieval. Одна дополнительная строка позволяет обнаружить превышение; отдельный `COUNT` мог бы устареть между подсчётом и выборкой при завершении индексации другим worker. Лимит применяется к суммарному набору выбранных collections каждого query, а не к `topK` и не отдельно к каждой коллекции.

До 5000 кандидатов включительно обрабатываются все выбранные готовые фрагменты. При превышении возвращается явная ошибка с лимитом и указанием сузить набор collections либо использовать индексируемый поиск. Снижение `topK` не уменьшает число кандидатов и не обходит ограничение. При нескольких queries ошибка откатывает весь retrieval: успешное событие, частичные источники и новые markers не сохраняются. Следующий допустимый запрос работает штатно.

Дополнительно исправлен порядок округления. Ранее cosine score округлялся до шести знаков **до** сортировки и `topK`. Для query `[1, 0]` старый точный вектор `[1, 0]` и более новый `[1, 0.0005]` получали одинаковый отображаемый score 1; `topK: 1` выбирал новый приблизительный фрагмент. Теперь сортировка, объединение queries и выбор `topK` используют неокруглённый score, а прежнее округление применяется только к итоговому ответу и сохранённым hits. Формат API не меняется; порядок близких результатов становится корректным относительно вычисленных значений cosine.

Это намеренное изменение поведения для больших наборов: прежний частичный успешный поиск становится отказом. Оно не увеличивает поддерживаемый объём и не добавляет pgvector/ANN. [Официальное описание pgvector](https://github.com/pgvector/pgvector#querying) различает точный поиск и приближённые индексы, у которых меняется полнота результатов. Отбор по времени индексации не является поиском ближайших соседей по всей коллекции. Индексируемый путь требует отдельной реализации и измерения качества/ресурсов.

## Проверки и границы

Новые [регрессии](../../../../apps/coordinator/test/knowledge-retrieval-capacity.test.ts) сначала упали на прежнем поведении: отсутствие ожидаемой ошибки для 5001 кандидата и выбор неверного документа при округлении близких score. После исправления проверены точный старый источник при 5000 кандидатах, отказ при 5001 в трёх коллекциях, rollback второго query без частичной записи, восстановление с последовательным marker и выбор правильного документа для обоих близких запросов. Вместе с прежними knowledge/validation-тестами — **10/10 pass**; полная регрессия coordinator — **223/223 pass**, coordinator typecheck — pass.

[Проверочное свидетельство](./evidence/2026-09-26/retrieval-capacity/checks.json) фиксирует исходный commit, SHA до/после, два ожидаемых failure до исправлений и итоговые логи. Исходник в архиве сверён с commit `99d3b83`; синтетический результат 5000/5001 перепроверен отдельно.

[Архив coordinator до изменения](./evidence/2026-09-26/retrieval-capacity/before-capacity-guard.json) сохраняет исходник, соответствующий прежним свидетельствам проверки размерности. Старые evidence и выводы не переписаны. Для этого изменения не проводились новый реальный embedding benchmark, PostgreSQL-нагрузка или проверка семантической достаточности источников. Проверка относится к полноте множества рассматриваемых кандидатов и явному отказу за поддерживаемой границей.
