# Pgvector: проверка совместимости большого retrieval

Дата среза: **27.09.2026**. Статус: **эксперимент выполнен; автоматическая замена backend отклонена**. Аудитория: разработчики coordinator, QA и владелец выпуска. Разрешение пользователя охватывает реализацию, push и merge в Agat; производственное внедрение нового хранилища этим опытом не выполнено. Ответственный за код и воспроизводимость — maintainer Agat; конкретный владелец будущих production SLO — TBD.

## Итог и рекомендация

Pgvector 0.8.6 нельзя прозрачно подставить вместо существующего float64 retrieval. На реальном PostgreSQL **17.11** подтверждены потеря различий при float32, ограничение размерностей HNSW и неполная выдача ANN после фильтрации. RLS в отдельном стенде сохранил изоляцию. Полный поиск pgvector по 6001 разрешённому вектору дал ожидаемые top‑20 для трёх синтетических запросов, но контрпример с близкими векторами нарушает совместимость независимо от ANN.

Решение для текущего выпуска: сохранить исходные JSON-векторы, double precision, полный перебор и явный лимит 5000. Следующее инженерное изменение — перенести тот же точный scorer к порционному чтению PostgreSQL в существующем worker SQL-моста. Это проверяемая оптимизация без отдельной векторной базы и без нового числового контракта. Рост лимита рассматривается только после замеров памяти/задержек и проверок отказа; здесь он не реализован.

## Охват, метод и границы доказательства

[Исполняемый probe](../../../../scripts/probe-pgvector.py) создаёт только новый собственный контейнер без сети и опубликованных портов, с лимитами 2 CPU и 2 ГиБ. Он не принимает URL чужой базы. Образ заранее скачивается отдельно и закреплён по digest; запуск использует `--pull=never`. По завершении контейнер и его анонимный том удаляются. Ни модели, ни реальные документы, ни бизнес-данные в этом опыте не используются.

План с hash входных файлов записан **до запуска SQL**. Код эксперимента закреплён commit `27da7b3`; [plan.json](./evidence/2026-09-27/pgvector-compatibility/plan.json) содержит полные SHA‑256. [Результат](./evidence/2026-09-27/pgvector-compatibility/result.json) связывается с планом по SHA, включает все 13 проверок, версии, идентичность образа, hits, ошибки и cleanup. [EXPLAIN ANALYZE](./evidence/2026-09-27/pgvector-compatibility/query-plans.json) подтверждает использование `probe_vectors_hnsw` во всех шести ANN-пробах.

Синтетический корпус: 6001 разрешённый фрагмент, 100 фрагментов исключённой коллекции того же проекта, 400 фрагментов другого проекта. Размерность 768, первые 16 координат ненулевые, остальные нули; генератор LCG32 с фиксированным seed. Полный payload COPY закреплён SHA‑256 `968ec7dc1a6c5f437e24f10e20333aba727df3e7f27feac17f6d94cc596b6718`. Три запроса: первая ось, вторая ось и первые 16 осей. Python `math.fsum` независимо вычисляет cosine и полный top‑20.

Это **одна сборка HNSW и один локальный запуск**, специально неблагоприятное расположение исключённых векторов, а не распределение реальных embeddings. Пробы принудительно включают HNSW, чтобы проверить именно его свойства; это не доказательство выбора индекса planner в эксплуатации. Числа `Execution Time` в EXPLAIN — диагностические одиночные значения, не benchmark, p95 или SLO. Приложение Agat, его полная schema/RLS, миграции, репликация и восстановление pgvector здесь не сертифицировались.

## Архитектура AS-IS

Worker вычисляет embeddings локально; coordinator проверяет lease, проект, закреплённые collection IDs, модель и размерность. Исходные документы, chunks, векторы, retrieval и provenance находятся в едином state store. SQLite читает iterator, PostgreSQL — транзакционный курсор порциями по 64 строки. SQL-worker передаёт порции JSON в синхронный coordinator, где проверяются все векторы и выбирается topK без раннего округления. Существуют отдельные роли runtime/tenant/migrator и прикладные проверки области доступа.

Бизнес-владелец документов и критерии семантического качества не меняются. Результаты модели не являются полномочиями на доступ. В этой оценке исследован только технический контракт чисел, кандидатов и границ доступа. Жизненный цикл существующих данных, backup/DR и маршрутизация решений остаются описанными в действующих документах Agat.

## Наблюдения и риски

| ID | Приоритет | Наблюдение | Влияние и проверка |
|---|---|---|---|
| GAP-001 | P1 | 12 допустимых float64-векторов стали одним `[1,1]` при сохранении в `vector(2)` | Лучший исходный кандидат №12 теряется при допустимом разрешении ties по ID; его нет даже в первых восьми для rerank. Зафиксированы оба порядка и исходные векторы |
| GAP-002 | P1 | HNSW не создал индекс для 4096D ни как `vector`, ни как `halfvec` — SQLSTATE `54000` | Нельзя незаметно уменьшить поддерживаемую размерность. Exact storage 4096D работает; смешанные размерности требуют фиксированного expression/partial index |
| GAP-003 | P1 | ANN сохранил RLS, но изменил recall и количество hits | Отсутствие утечки не доказывает полноту поиска. Фильтр проекта/коллекции и один общий граф недостаточны для текущей гарантии topK |
| GAP-004 | P2 | Текущий полный перебор ограничен 5000 и пересылает все выбранные векторы SQL-worker → coordinator | Следующий шаг — тот же scorer внутри SQL-worker, затем отдельная проверка увеличенного объёма. Простое повышение числа увеличивает работу O(N×D) |

В контрпримере кандидат №12 — `[1,1]`, остальные — `[1,1+i×10⁻⁹]`; запрос `[1,0]`. В исходной арифметике №12 строго лучше. После преобразования значения совпадают, а исходное различие восстановить по `vector` нельзя. [Прикладной regression test](../../../../apps/coordinator/test/knowledge-retrieval-capacity.test.ts) проверяет сохранение старого лучшего документа в реальном `AgatStore.searchKnowledge`, несмотря на одинаковые публичные округлённые score.

На основном синтетическом корпусе exact pgvector сохранил три порядка top‑20; максимальная ошибка score относительно float64 oracle — **5,70×10⁻⁸**. Это положительный результат конкретных данных, не опровержение контрпримера.

| HNSW, `ef_search=40` | Запрос | Число hits | Recall@20 относительно exact pgvector |
|---|---|---:|---:|
| iterative scan off | Первая ось | 0 | 0% |
| iterative scan off | Вторая ось | 20 | 65% |
| iterative scan off | Первые 16 осей | 20 | 90% |
| strict_order | Первая ось | 20 | 15% |
| strict_order | Вторая ось | 20 | 65% |
| strict_order | Первые 16 осей | 20 | 90% |

Все возвращённые hits принадлежат нужному проекту и коллекции. До индексирования проверены отдельный runtime без superuser/BYPASSRLS, отсутствие/сброс scope, cross-project SELECT, запрет INSERT SQLSTATE `42501`, DELETE чужого проекта с нулём изменённых строк. Это контроль отдельной политики стенда, не замена Fleet/HA-тестов Agat.

## Варианты и целевая рекомендация

| Критерий | Точный float64 в существующем SQL-worker | Pgvector exact | Pgvector HNSW / внешний ANN-сервис |
|---|---|---|---|
| Числовой контракт | Сохраняется при переиспользовании scorer; нужно доказать тестами | Float32 меняет возможный topK — GAP-001 | Float32/quantization и ANN требуют отдельного контракта качества |
| Все текущие размерности | Без новой границы 1–4096 | Хранение достаточно; арифметика отличается | HNSW vector/halfvec не покрывают 4096; внешний сервис не проверен |
| Изоляция и данные | Те же SQL, snapshot, роли и source of truth | Те же роли, но новая миграция и тип | Общий граф влияет на recall; разделение по project/model/dimension и lifecycle требуют проекта |
| Стоимость и задержка | O(N×D); меньше обменов JSON между потоками, эффект ещё не измерен | O(N×D), новые extension и deployment | Потенциально быстрее; индекс/синхронизация, перестроение и мониторинг recall — дополнительные расходы |
| Решение текущего этапа | Выбран следующий ограниченный прототип | Прозрачная замена отклонена | Отложено до отдельного opt-in контракта и независимого eval |

**TO-BE ближайшего выпуска:** исходные JSON-векторы остаются авторитетными, scorer использует ту же проверку и арифметику, DB-worker возвращает только ранжированные кандидаты. Query/lease/project checks, ошибки повреждённых векторов, snapshot, marker/provenance и rollback сохраняются. Новое хранилище и изменение схемы не нужны для такого прототипа. Успех определяется совпадением исходных hits и измеримым снижением обменов, а не уменьшением работы за счёт потери кандидатов.

**Стратегический TO-BE:** ANN возможен как отдельный явно выбранный профиль поиска со своим contract/version, размерностями, измеренным recall и fallback. До его реализации требуется схема изоляции project/model/dimension, атомарная синхронизация индекса с документом, reindex/delete/backup/restore и migration/admission. Внешняя векторная БД сейчас не оправдана доказанными требованиями: она создаёт второй жизненный цикл данных, а сравнительного выигрыша не измерено (INF).
