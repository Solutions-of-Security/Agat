# Совместная нагрузка decider и локального генератора

26.09.2026. Два прогона на Apple M1 Max, 32 ГиБ, подтвердили выполнение закреплённых `Mapika/decider-2b` и `qwen3:8b` в одном локальном окружении. Всего 240 измеряемых вызовов и восемь прогревов, без ошибок, изменения профиля или ответов. При перекрытии HTTP-запросов задержки обеих моделей выросли. Это ограниченный ресурсный опыт; качество, production SLO и полноценный primary workflow не квалифицированы.

## Метод и границы

[Инструмент](../../../../scripts/benchmark-decision-shared-load.py) использует тот же sealed development-export из 15 случаев. Holdout/calibration, Score и слишком большие запросы отвергаются до обращения к сервисам. Gold labels, исходные тексты и сгенерированный текст в отчёт не включены. Входы закреплены hashes, результаты — подписями типизированного решения; ответные вероятности генератора не извлекаются из текста.

Decider обслуживает настоящий `LocalDecisionClient`, runtime `0.6.0`, cache 128 МиБ, максимум 2048 токенов. Профиль `9fe09d8472eb5304218eb8e3b3bbd10ae20659e67199768f73a551a372b85cb0` сверяется до и после опыта. Primary — локальный генератор структурированной метки через Ollama 0.34.2, `qwen3:8b`, Q4_K_M, digest `500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41`. Параметры: `think=false`, temperature 0, seed 0, context 8192, максимум 128 выходных токенов. Перед каждым вызовом проверяется digest. Модель и шаблон те же, что в [генеративном baseline](../baselines/README.md).

Ollama запущен отдельным тестовым процессом на loopback с `OLLAMA_NO_CLOUD=1`, `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_NUM_PARALLEL=1`; существующие веса не скачиваются заново. Параллельность Ollama и контекст влияют на расход памяти, поэтому они заданы явно по [официальной документации](https://docs.ollama.com/faq). В каждом из семи снимков `/api/ps` модель загружена с context 8192, `size = size_vram = 6 177 989 590` байт, около 5.754 ГиБ. Это значение [API загруженных моделей](https://docs.ollama.com/api/ps), не непрерывный максимум совместной памяти процессов.

После двух прогревочных пар идут шесть фаз: decider отдельно → primary отдельно → primary и затем decider → одновременный старт двух независимых запросов → primary отдельно → decider отдельно. Каждый вход используется один раз за фазу, по одному активному запросу на модель; retry и скрытой очереди измеритель не добавляет. Обе модели остаются загруженными и в контрольных фазах.

Последовательная пара соответствует порядку primary → shadow у одного worker. Перекрывающаяся пара представляет независимую конкурентную работу, например запрос другого worker. Зафиксировано перекрытие интервалов HTTP-вызовов, а не одновременное исполнение GPU kernels. Не измеряются GPU utilization, доля общей пропускной способности production-системы или полный процесс агента. Загрузка исключена из фазовых задержек; прогревы сохранены отдельно.

## Результаты

В каждой непустой ячейке — p50 / p95, мс, по 15 вызовам. При таком размере nearest-rank p95 равен максимуму; это слабая оценка хвоста. Первый [отчёт](./evidence/2026-09-26/shared-qwen3-decider.json) завершился за 61.868 с, [повтор на тех же сервисах](./evidence/2026-09-26/shared-qwen3-decider-repeat.json) — за 37.748 с, включая прогревы и проверки.

| Фаза | Decider, опыт 1 | Primary, опыт 1 | Decider, повтор | Primary, повтор |
|---|---:|---:|---:|---:|
| Decider до | 195.275 / 294.833 | — | 198.006 / 287.952 | — |
| Primary до | — | 1317.495 / 1721.860 | — | 258.383 / 1224.996 |
| Последовательно | 215.812 / 1686.067 | 249.841 / 1213.848 | 210.109 / 1636.511 | 241.186 / 1176.780 |
| С перекрытием | 318.718 / 537.347 | 391.773 / 1503.535 | 305.457 / 547.676 | 390.758 / 1546.585 |
| Primary после | — | 229.724 / 1179.031 | — | 218.998 / 1173.476 |
| Decider после | 209.151 / 1680.455 | — | 204.233 / 297.827 | — |

В каждом опыте выполнено 60 вызовов decider и 60 primary; busy, timeout и ошибки протокола отсутствуют. Входы decider — 152–591 токен, primary — до 938, выход primary — до 11 токенов. Контрольные подписи решений обеих моделей совпали для каждого входа во всех фазах и между опытами. Это повторяемость, а не проверка правильности меток.

В первом проходе primary до нагрузки заметно медленнее последующих фаз. Повтор на прогретых сервисах уменьшил это различие. Prompt caches, температурный режим и другие приложения не контролируются; этот результат нельзя приписать только конкуренции. Перекрывающаяся фаза в обоих опытах имеет более высокую медиану, чем соседние прогретые одиночные фазы, у обеих моделей.

Первый decider-запрос после фазы primary в последовательной паре занял 1686.067 и 1636.511 мс. В первом опыте похожий пик появился и в последней контрольной фазе. Причина не установлена; эти пики нельзя вычеркнуть как «неудачный прогрев». Медиана также не описывает их влияние на deadline. Подтверждённый вывод для текущего shadow: ограничивать конкурентность, учитывать задержку primary и сохранять fallback; оснований повышать concurrency или обещать задержку менее секунды нет.

[Независимый пересчёт](./evidence/2026-09-26/shared-load-verification.json) проверил seals, hashes текущего инструмента, входы, все counts, p50/p95 по сырым длительностям, интервалы/перекрытие и подписи ответов. Уникальных development-входов остаётся 15; эти 240 вызовов не создают новые независимые примеры качества. Тестовые сервисы остановлены после измерения.

## Воспроизведение

Запустите decider с `--cache-limit-mib 128` по [инструкции runtime](../../../local-decision-runtime.md). В отдельном терминале запустите тестовый Ollama на свободном loopback-порту:

```bash
OLLAMA_HOST=127.0.0.1:11535 OLLAMA_NO_CLOUD=1 \
OLLAMA_MAX_LOADED_MODELS=1 OLLAMA_NUM_PARALLEL=1 \
OLLAMA_CONTEXT_LENGTH=8192 OLLAMA_KEEP_ALIVE=5m ollama serve

python3 scripts/benchmark-decision-shared-load.py \
  --decision-url http://127.0.0.1:8766 \
  --primary-url http://127.0.0.1:11535 --primary-model qwen3:8b \
  --expected-primary-digest 500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41 \
  --dataset docs/qualification/local-decisions/development/evidence/2026-09-26/dataset.json \
  --rounds 1 --warmup 2 --time-budget-s 300 \
  --output docs/qualification/local-decisions/performance/evidence/new-run/shared-load.json

python3 -m unittest scripts.test.test_decision_shared_load -v
```

Повтор использует те же команды и сервисы, с новым output. План допускает максимум 30 входов, два прохода, 240 измеряемых вызовов и 600 секунд; бюджет проверяется между парами. Primary HTTP timeout — 30 с, decider — до 10 с. Эти deadlines не гарантируют отмену запущенной GPU-работы. Неполный план, ошибка, изменение профиля или ответа decider сохраняются как `degraded`, exit code 1. Существующие файлы не перезаписываются.

Шесть автоматических проверок покрывают настоящее перекрытие тестовых вызовов, разделение фаз/ошибок, неизменность привязки к профилю, сохранение неполных результатов, запрет holdout/избыточного плана до сети и отсутствие source/gold/exception text. Они входят в `npm run docs:check`.
