# Проверка lease после ожидания и расчёта retrieval

Дата: **27.09.2026**. [Проверка при входе](./retrieval-lease-validity.md) отклоняет уже истёкший lease, но не защищала от изменения состояния во время поиска. Подготовка [изолированного исполнителя](./retrieval-isolated-executor.md) воспроизвела две гонки на PostgreSQL: lease истекал при ожидании run lock; другая транзакция отменяла stage, пока retrieval использовал прежний снимок.

## Изменение

При входе остаётся проверка узла, lease, `running` и времени. Валидация коллекций и точный ranking выполняются до PostgreSQL row locks. После расчёта код заново читает действующую stage с `FOR UPDATE`, проверяет её идентичность и затем блокирует run для выделения маркеров. Проверяется неизменность project/knowledge snapshot запуска и текущее время после получения блокировок. Только затем создаются retrieval и событие.

Порядок stage → run соответствует обычному завершению lease и отмене run. Короткий участок с row locks позволяет продлению и отмене выполнять запись во время чтения индекса. SQLite сохраняет существующую транзакцию `BEGIN IMMEDIATE` и дополнительно проверяет срок перед сохранением; его single-writer ограничение не устранено.

[PostgreSQL описывает повторную проверку изменённой строки в Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html) и [удержание row locks до конца транзакции](https://www.postgresql.org/docs/17/explicit-locking.html). Проверка времени выполняется ещё раз после ожидания: bound timestamp первоначального SELECT сам по себе не обновляется, пока SQL ждёт lock.

Это повторная проверка перед записью после ranking и SQL-ожидания. Мгновение фактического commit, глобальная отмена уже выполняемой операции и отзыв token во время активного запроса не получают нового обещания. Обработка конфликтующих изменений других операций coordinator требует отдельных проверок отзывчивости.

## Проверки

На baseline `e84ef0bc503407df853cb184080eaad99d3222c9` оба первых сценария завершились assertion failure: поиск действительно принял истёкший lease и старое состояние отменённой stage. Тесты сначала наблюдают ожидание SQL-lock, затем освобождают конкурирующую транзакцию. [Статистический snapshot PostgreSQL сбрасывается](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-STATS-VIEWING) перед каждым наблюдением; без этого первая версия теста читала прежний текст запроса.

Финальные PostgreSQL-сценарии проверяют:

- истечение lease во время ожидания run lock, отсутствие записей и восстановление по новому lease с `K1`;
- отмену stage/run конкурирующей транзакцией до завершения поиска;
- истечение после начальной проверки, пока чтение индекса заблокировано;
- успешное продление lease другой транзакцией во время чтения индекса и последующее сохранение результата.

SQLite-тест управляет только часами во время потребления настоящего candidate iterator: истечение отклоняется без retrieval/event, новый lease получает `K1`. Перед переназначением возобновлён heartbeat, поскольку модельные часы перескочили также порог свежести node. Общий coordinator: **243/243**, типизация и сборка приложений прошли.

Fixture теперь завершает собственный run при очистке. Полный повтор: **17/17 pass**.
