# Отзывчивость HTTP при точном retrieval

Дата протокола: **27.09.2026**. Статус: два локальных опыта завершены, корректность ответов сохранена, обнаружены задержки health до нескольких секунд. Предыдущий [рост корпуса](./retrieval-search-budget.md) проверил корректность одиночных store-вызовов. Здесь проверяется очередь HTTP и задержка `/api/v1/health` во время поисков.

## Вопрос и границы

SQLite выполняет scorer в основном потоке coordinator; PostgreSQL выполняет его в SQL-worker, но coordinator ожидает синхронный мост. Поэтому меньший расход памяти не доказывает отзывчивость HTTP. [Node.js рекомендует ограничивать блокирующую работу основного потока](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop); [worker threads](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html) сами по себе не устраняют синхронное ожидание вызывающего потока.

Опыт использует настоящий `createCoordinatorServer`, worker bearer authentication и `AgatStore`, но отдельный Python-процесс нагрузки. Генерация ответа, Ollama, shadow, бизнес-коннекторы и Temporal отсутствуют. Внутренний setup создаёт disposable документы и leases; это диагностический HTTP-стенд, а не полный сценарий production startup.

## Профиль, фиксируемый до измерений

- Один coordinator-процесс на backend, SQLite и одноразовый PostgreSQL 17.6 по очереди; Node 24.
- 9716 синтетических фрагментов, dimension 768, topK 1, операторский бюджет 10000. Один старый точный вектор и ортогональные остальные дают программно известный единственный результат. Значения ±1/3 создают длинный JSON. Это нагрузочный fixture, а не семантический benchmark.
- Один прогрев поиска до измерений. Контроль health в течение двух секунд без retrieval; затем три последовательных всплеска для каждого уровня 1, 2 и 4 одновременно отправленных поисков. Между всплесками leases завершаются. Всего 21 измеряемый поиск на backend.
- Python barrier запускает поиски всплеска; фактическое пересечение HTTP-интервалов проверяется отдельно от настроенного числа клиентов. Один клиентский запрос не повторяется автоматически.
- Health планируется каждые 100 мс отдельным клиентским потоком, максимум четыре запроса в полёте. Невыпущенный probe записывается явно; статистика успешных probes не скрывает пропущенные интервалы. Учитываются опоздание выпуска и ошибки, не только latency полученных 200.
- Node `monitorEventLoopDelay` с resolution 10 мс фиксирует задержку основного потока по каждой фазе; клиентские интервалы измеряются независимым monotonic clock. Точность таймеров не предполагается идеальной.

Каждый успешный поиск должен вернуть старый точный документ, score 1, marker K1 и ровно одно сохранённое retrieval event. Тестовые токены остаются в памяти/одноразовом каталоге. Все endpoint — `127.0.0.1`, внешние сервисы не используются. Свои дочерние процессы, контейнер и данные очищаются при успехе и ошибке.

После первого наблюдения добавлена отдельная проверка числа готовых кандидатов непосредственно в БД с фильтрами project, collection, model, dimensions и document status. Она дополняет счётчик успешно переданных embeddings; для подтверждения результата проводится новый полный прогон с новым commit, исходный опыт сохраняется отдельно.

## Критерии интерпретации

Реализация и протокол фиксируются commit до запуска. Launcher отклоняет Node другой major-версии и незакоммиченные изменения файлов стенда и выбранных исходных файлов coordinator.

```bash
python3 scripts/run-rag-http-probe.py \
  --evidence-dir docs/qualification/local-decisions/performance/evidence/new-http-probe
python3 scripts/verify-rag-http-probe.py \
  --evidence-dir docs/qualification/local-decisions/performance/evidence/new-http-probe
```

До опыта не устанавливается произвольный production SLO. Сохраняются все поиски, HTTP-ошибки, health probes и пропуски их выпуска, latency, event-loop delay, версии и хеши кода. Нарушение правильности результата или cleanup делает прогон неполным. Задержка health является наблюдением, которое определяет следующий инженерный шаг, а не условием скрытого удаления неудачного опыта.

Всплески — закрытая модель нагрузки, не фиксированная интенсивность production-трафика. Проверка health имеет ограниченное число запросов в полёте; по одному её latency percentile нельзя оценивать доступность. RSS процесса, если записан, включает подготовку синтетического индекса. На общей машине влияние другой пользовательской нагрузки не отделяется. Оценка нескольких replicas, throughput/SLO, cancellation, Temporal и предметное качество остаются отдельными вопросами.

[Первый опыт](./evidence/2026-09-27/retrieval-http-initial/verification.json) на commit `696b448f0b384b9da1e09e59f7763af08d3d4b5e` и [повтор с SQL-подсчётом](./evidence/2026-09-27/retrieval-http-counted/verification.json) на `e441381553270c2c84285c7affba3da8dc93bbb9` независимо проверены: по 42/42 измеряемых поиска и два прогрева в каждом опыте. Повтор подтвердил ровно 9716 готовых кандидатов в каждой БД. Все ответы содержат ожидаемый документ, score, provenance и marker; каждый run имеет одно retrieval event. Во всех всплесках клиентские интервалы действительно перекрывались на заданном уровне.

Первый опыт дал максимум health 1625 мс SQLite и 6942 мс PostgreSQL при четырёх поисках. Разница между опытами не доказывает ускорение: продуктовый путь поиска не менялся, а нагрузка общей машины и планирование потоков не контролировались. В повторе не зафиксировано HTTP-ошибок среди отправленных запросов; пропуски выпуска probes являются отдельным результатом, а не успешными запросами и не production error rate.

Максимальная задержка health может превышать максимальную задержку таймера Node: запрос остаётся в очереди между несколькими синхронными участками. Поэтому 5,4 секунды health не выдаются за один непрерывный 5,4-секундный блок event loop. Вместе с непосредственным вызовом синхронного `store.searchKnowledge` в HTTP-handler результат подтверждает проблему отзывчивости одного coordinator при длинном точном поиске.

## Следующее изменение

Следующий шаг — прототип отдельного исполнителя полного retrieval с асинхронным ожиданием HTTP и ограниченной очередью. В существующий `AgatStore.transaction()` нельзя просто вставить `await`: он синхронно выполняет COMMIT после callback, хранит общий `transactionDepth` и не изолирует чередующиеся запросы. Один владелец отдельной транзакции должен сохранить текущие проверки lease, credentials, project/RLS, snapshot и атомарную запись citations.

Для SQLite дополнительно требуется проверять конкуренцию записей: WAL допускает одновременных читателей, но [писатель остаётся один](https://sqlite.org/wal.html). Другая синхронная запись в основном потоке способна снова задержать HTTP. Для PostgreSQL нужен отдельный runtime connection и повторная проверка credentials после ожидания в очереди. Ошибка или завершение исполнителя не должны вызывать повтор уже начатого запроса автоматически. Эти условия и работа фонового maintenance требуют отдельной проверки до включения нового пути в coordinator.
