# Новые снимки локального CSV и сравнение изменений

26.09.2026. Добавлена однократная подготовка из явно выбранного локального файла: **стабильное чтение → SHA новых байтов → расчёт заявок → сравнение с прежним bundle → отдельный каталог для проверки**. [Прежний адаптер](./request-records.md) требовал заранее записать SHA и последнюю строку в mapping; новый рецепт фиксирует смысл полей, а SHA и конец таблицы определяются по захваченным байтам.

CLI выполняет один запуск. Публикация в приложении и решение владельца остаются в существующем [процессе согласования](./source-process.md). Этот этап не подключает бизнес-систему и не задаёт расписание.

## Явный рецепт

[Рецепт примера](./evidence/2026-09-26/source-snapshots/recipe.json) имеет версию `agat.report.request-snapshot-recipe.v1`. Он содержит имя процесса, точность отображения, номер строки заголовка, `through: end_of_file` и mapping отдельных заявок без `expectedSha256`/`table`. Колонки, два периода, единицы, ключ дублей и декларации совокупности остаются обязательными. Файл читается от указанного заголовка до EOF: поиск таблицы и удаление footer не выполняются. Лишний период, итоговая строка или конфликтующий дубль приводят к отказу.

```bash
python3 scripts/prepare-report-snapshot.py \
  --source docs/qualification/local-decisions/performance/evidence/2026-09-26/source-snapshots/exports/initial.csv \
  --recipe docs/qualification/local-decisions/performance/evidence/2026-09-26/source-snapshots/recipe.json \
  --output-dir docs/qualification/local-decisions/performance/evidence/new-snapshot/initial

python3 scripts/prepare-report-snapshot.py \
  --source docs/qualification/local-decisions/performance/evidence/2026-09-26/source-snapshots/exports/updated.csv \
  --recipe docs/qualification/local-decisions/performance/evidence/2026-09-26/source-snapshots/recipe.json \
  --previous-bundle docs/qualification/local-decisions/performance/evidence/new-snapshot/initial/bundle.json \
  --output-dir docs/qualification/local-decisions/performance/evidence/new-snapshot/updated

python3 scripts/verify-report-snapshot.py \
  --snapshot docs/qualification/local-decisions/performance/evidence/new-snapshot/updated \
  --previous-bundle docs/qualification/local-decisions/performance/evidence/new-snapshot/initial/bundle.json
```

[Подготовка](../../../../scripts/prepare-report-snapshot.py) создаёт новый каталог под `docs` с `source.csv`, `mapping.json`, `report.md`, `calculation.json`, `bundle.json`, `process.json` и `snapshot.json`. Исходный CSV копируется побайтово. Последним записывается receipt `snapshot.json`; затем CLI повторно проверяет все файлы. При отказе чтения или расчёта каталог не создаётся. Ошибка файловой записи может оставить неполный каталог; его нельзя считать готовым снимком, существующий путь не перезаписывается.

## Чтение и изменения

[Библиотека](../../../../scripts/lib/report_snapshot.py) открывает обычный файл через POSIX-дескриптор с `O_NOFOLLOW` и `O_NONBLOCK`; symlink в последнем компоненте пути, FIFO, каталог, пустой файл и источник больше 2 МиБ отклоняются. Родительские каталоги могут содержать symlink; это не механизм изоляции файловой системы. Выполняются два ограниченных чтения через один дескриптор. Сравниваются байты и метаданные до, между и после чтений, а также объект по исходному пути: device/inode, размер, `mtime_ns`, `ctime_ns`. Изменение или замена во время захвата приводит к явной ошибке, автоматического retry нет.

Это обнаружение наблюдаемых изменений, а не блокировка писателя или транзакционный снимок бизнес-системы. Производителю выгрузки следует завершить запись и публиковать готовый файл атомарной заменой в той же файловой системе. Сохранённая копия проверяется по SHA независимо от последующих изменений live-файла. SHA/seal проверяют целостность, но не удостоверяют автора.

При наличии `--previous-bundle` прежний bundle заново проверяется по его собственному CSV. Для сравнения должны совпасть URI/ID источника, поля, периоды, единицы, совокупность, правило дублей, строка заголовка, имя процесса и точность. Изменение контракта требует отдельного baseline. Предыдущий источник не заменяется новым и его SHA не обновляется на месте.

| Случай | Результат |
|---|---|
| Первый допустимый CSV | Новый снимок со статусом `prepared_requires_review`, сравнение `initial` |
| Байты совпадают с предыдущим bundle | `unchanged`, exit 0, новый каталог не создаётся |
| Байты изменились | Новый снимок, SHA предыдущего bundle и сравнение `changed` |
| Изменилась только преамбула | Новый source SHA; table SHA и суммы могут остаться прежними |
| Добавился одинаковый дубль | Новый source/table SHA и количество повторов; суммы могут остаться прежними |
| Конфликт, иной контракт, нестабильное чтение или превышение лимита процесса | Явный отказ; прежний снимок сохраняется |

Receipt отдельно показывает `sourceBytesChanged`, `tableBytesChanged`, `aggregateValuesChanged`, количества исходных/уникальных записей и суммы каждого периода до/после. `verify-report-snapshot.py` пересобирает mapping, расчёт, Markdown и процесс по сохранённому CSV, сверяет все шесть файлов и сравнение. Для обновлённого снимка нужен именно предыдущий bundle; без него проверка сравнения отклоняется. Она подтверждает эту пару, а не всю неявную историю изменений. Старые реализации требуют своих архивных исходников; переносить verification на изменённый код нельзя.

Сохраняется лимит подготовленного процесса: 100 000 символов literal JSON после экранирования. Проверен отказ на большом протоколе дублей без усечения и выходного каталога. Полнота выгрузки, достоверность, фактическая семантика ID/единиц и предметное согласование не устанавливаются; соответствующие flags остаются `false`.

## Доказательства

[План опыта](./evidence/2026-09-26/source-snapshots/plan.json) заранее закрепил рецепт, три авторских CSV, ожидаемые изменения и SHA кода. [Первый receipt](./evidence/2026-09-26/source-snapshots/initial/snapshot.json) содержит 6 строк / 4 уникальные пары / 2 повтора. [Обновлённый receipt](./evidence/2026-09-26/source-snapshots/changed/snapshot.json) после добавления заявки: 7 строк / 5 уникальных пар / 2 повтора; июль — 3 заявки, 4,5 часа и один признак. [Отчёт обновления](./evidence/2026-09-26/source-snapshots/changed/report.md): среднее 1,5 → 1,5 часа, доли 33,333% → 50%.

[Шесть CLI-вызовов](./evidence/2026-09-26/source-snapshots/cli-runs.json) завершились ожидаемо: подготовка initial/changed, `unchanged` без каталога, конфликт с exit 2 без каталога, независимая повторная проверка обоих снимков. [Verification](./evidence/2026-09-26/source-snapshots/verification.json) связывает план, оба receipt и исходные SHA. Это авторские синтетические данные; новых бизнес-источников или человеческих решений в опыте нет.

Девять новых [тестов](../../../../scripts/test/test_report_snapshot.py) покрывают изменение файла на месте, подмену пути, разные байты при неизменных метаданных, symlink/FIFO, предел размера, изменение только преамбулы/дублей, иной контракт, повторно запечатанные подмены, CLI и сохранность прошлого снимка. Вместе со всей арифметикой и процессом — **47/47 pass**. Полный `docs:check` до добавления этого пояснения — **12 Node- и 135 Python-тестов — pass**. Новое браузерное поведение не добавлено: подготовленный граф проходит прежний путь согласования; публикация этих снимков в пользовательское приложение не выполнялась.

Решение использует [Python `os.fstat` и наносекундные поля](https://docs.python.org/3/library/os.html#os.fstat), [проверку обычного файла](https://docs.python.org/3/library/stat.html#stat.S_ISREG) и свойство успешного атомарного переименования на одной файловой системе у [`os.replace`](https://docs.python.org/3/library/os.html#os.replace). Точность временных меток зависит от ОС/файловой системы, поэтому чтение проверяется также по байтам.
