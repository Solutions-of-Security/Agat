# RAG: порционное чтение векторов из PostgreSQL

26.09.2026. Исправлен отказ поиска внутри поддерживаемой границы: **500 корректных
4096-мерных векторов уже превышали лимит одного ответа PostgreSQL-моста**.
Теперь coordinator читает кандидатов через курсор порциями по 64 строки и
сохраняет в памяти ранжирования только `topK`. Лимит 5000 кандидатов и явный
отказ при его превышении сохраняются.

## Воспроизведение и повтор

[План](./evidence/2026-09-26/retrieval-streaming/plan.json) зафиксирован до опыта.
Одноразовый PostgreSQL 17.6 получил 500 фрагментов через обычные методы ingestion
и 16 embedding leases. Каждый вектор состоит из 4096 значений `1 / 3`;
его JSON занимает 77 825 байт. Это допустимые синтетические данные, без модели
и бизнес-источников. Запрашивается `topK: 1` тем же вектором.

| Проверка | До изменения | После |
|---|---|---|
| Готовых кандидатов / измерений | 500 / 4096 | 500 / 4096 |
| Поиск | `PostgresResponseTooLarge`: 39 470 356 байт при лимите 33 554 432 | Успешен, один hit |
| Событий retrieval | 0 | 1 |

Сохранены [исходный результат](./evidence/2026-09-26/retrieval-streaming/before.json),
[повтор](./evidence/2026-09-26/retrieval-streaming/after.json),

Скрипт содержит абсолютные пути исследовательской машины и закрепляет старое
ожидаемое падение; переносимая текущая проверка включена в интеграционный suite.

## Выбор реализации

[PostgreSQL DECLARE](https://www.postgresql.org/docs/17/sql-declare.html) позволяет
читать один результат запроса частями. Использован `NO SCROLL CURSOR WITHOUT HOLD`
в уже существующей транзакции retrieval: последовательные `FETCH` сохраняют
snapshot курсора, `CLOSE` выполняется и при досрочном выходе. Если SQL-ошибка
прерывает транзакцию, ошибка закрытия не скрывает первоначальную причину;
rollback освобождает курсор. Повторные запросы `LIMIT/OFFSET` при Read Committed
могли бы наблюдать разные наборы строк.

В SQLite используется штатный
[`StatementSync.iterate`](https://nodejs.org/api/sqlite.html#statementiterate-namedparameters-anonymousparameters),
доступный с заявленного проектом Node.js 22.13. Новых библиотек и миграции схемы нет.

[Общий код поиска](../../../../apps/coordinator/src/database.ts) обрабатывает
тот же SQL с пределом 5001. Счётчик при чтении отклоняет 5001-го кандидата;
все записи retrieval выполняются только после успешной проверки всех queries.
Каждый прочитанный вектор проверяется, даже когда его score не входит в topK.
Неокруглённые score определяют порядок, равные score сохраняют порядок выдачи
SQL, округление применяется к итоговым hits. Полный массив всех vectors и всех
ранжированных hits в coordinator больше не создаётся.

## Границы результата

Это исправление передачи и хранения промежуточных данных, а не ANN-индекс.
SQL всё ещё выбирает и упорядочивает кандидатов, cosine вычисляется для каждого
из них. Порции ограничены числом строк, не отдельным новым лимитом байт; прежний
32-МиБ предел каждого ответа моста остаётся защитой для повреждённых или иных
необычно крупных строк. Расход памяти PostgreSQL, RSS и throughput этим опытом
не квалифицированы. Семантическое качество embeddings не измерялось.

Для коллекций свыше 5000 остаётся отдельный этап масштабирования. Возможный
pgvector/ANN-путь требует своего контракта и измерения recall: по
[официальному описанию pgvector](https://github.com/pgvector/pgvector#indexing)
приближённый индекс может менять полноту результатов. Эта оптимизация не
включает новый способ ранжирования или автоматическую маршрутизацию решений.
