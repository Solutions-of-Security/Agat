# HTTP-профиль индексации и продления аренды

Дата: **27.09.2026**. План фиксируется до измерения, после [защиты общей размерности коллекции](./embedding-dimension-concurrency.md). Цель — наблюдать стоимость реальных completion, renewal, health и maintenance после изменений владения и SQL-блокировок.

## Фиксированный протокол

Одна неизменная версия исходников и собранных JS-файлов, Node 24, PostgreSQL 17.6-alpine. Два обычных процесса `apps/coordinator/dist/server.js` и отдельный fixture-процесс работают с одноразовой локальной БД. Оба main используют стандартный sync executor и реальный maintenance каждые 1000 мс. PoolMax каждой роли main — 4, fixture — 1; admission рассчитывается на 3 процесса с верхней границей poolMax=4. Разные coordinator instance IDs исключают перезапись liveness друг друга.

Последовательно выполняются две схемы коллекций на отдельных одноразовых PostgreSQL: **shared**, затем **independent**. В первой все документы измеряемой фазы имеют одну коллекцию; во второй каждый документ имеет собственную. Все модели и тексты синтетические; inference не вызывается. Партия содержит 32 chunks, каждый вектор — 768 значений `1/3`, исходный документ — 12800 ASCII-символов с уникальным префиксом. Сохраняются хэши документа, идентификаторов chunks и точного JSON вектора.

В каждой схеме: два одновременных warmup completion (по одному на main), idle 2 секунды, затем три повтора для конкурентности **1 / 2 / 4**. Каждая измеряемая фаза содержит `10 × concurrency` completion, распределённых по main по очереди. Получается **210 измеряемых completion + 2 warmup** на схему, **420 + 4** на пару, **13568 векторов**. Генератор держит не более 4 completion в работе и не более 40 заранее подготовленных заданий в фазе; это конечная closed-loop нагрузка, а не оценка максимальной входной интенсивности.

Независимый Python-процесс планирует health каждые 100 мс, renewal каждые 250 мс, с максимумом 4 ожидающих запросов каждого вида. Renewal чередует stage/embedding и обе реплики на отдельных действующих lease, не конкурирующих с завершением тех же jobs. Невыпущенные probes и lateness сохраняются; их нельзя удалять при подсчёте задержек. Wall time включает клиентскую JSON-сериализацию и HTTP-ответ. Для каждого main наблюдатель фиксирует event-loop delay, RSS и фактические вызовы штатного maintenance; он не запускает собственный maintenance.

## Условия принятия свидетельства

Каждый completion должен вернуть 200, `completed=true`, `remainingChunks=0`. Независимый fixture читает сохранённые chunks и проверяет точные IDs, число, модель, размерность и SHA JSON-вектора. Document должен быть ready, job — completed с очищенным owner/lease, failures=0, и должно существовать ровно одно ready-событие с правильным embeddedChunks/dimensions. Все отправленные health должны вернуть 200, все renewal — 204; действующие контрольные lease сохраняют владельца и не сокращают срок.

Replay проверяет фиксированную сетку фаз и конкурентность по интервалам каждого HTTP-запроса, обе схемы коллекций, полноту документов, реальные maintenance во время нагрузки на обеих репликах и вызовы обоих видов renewal. Проверяются source SHA из закреплённого git commit, хэши compiled JS, общий image ID, clean exit четырёх main и двух fixture-процессов, удаление обоих собственных контейнеров. Ошибка даёт `incomplete`; повтор использует новый каталог и сохраняет прежний отказ.

```sh
python3 scripts/run-embedding-http-probe.py --evidence-dir docs/qualification/local-decisions/performance/evidence/2026-09-27/embedding-http
python3 scripts/verify-embedding-http-probe.py --evidence-dir docs/qualification/local-decisions/performance/evidence/2026-09-27/embedding-http
```

На момент фиксации протокола результатов ещё не было. Наибольшая длительность maintenance в нагрузочных фазах: **23,285 → 17,300 мс**; event-loop max — **118,292 → 103,219 мс**.

Lifetime peak RSS двух main составил **270860288 / 268779520 bytes** для shared и **262176768 / 271532032 bytes** для independent. Отчёт launcher содержит 56,448 секунды от начала его измеряемого участка до cleanup. Начальная load average 1/5/15 минут — **12,87 / 19,21 / 17,84**, конечная — **12,70 / 17,99 / 17,48**. Четыре main и два fixture завершились с кодом 0, оба собственных контейнера удалены, все шесть PID отсутствовали при дополнительной проверке.

[Полные данные](./evidence/2026-09-27/embedding-http/launcher-result.json) содержат checksum каждого измерительного файла. [Проверки и SHA](./evidence/2026-09-27/embedding-http-checks/checks.json) включают независимый replay, 13 тестов против неполного или согласованно перехэшированного свидетельства и проверку завершения процессов. После измерения replay дополнительно стал разбирать ISO-даты контрольных lease, чтобы повреждённая строка не проходила лексикографическое сравнение; измеренный runtime и генератор запросов не изменялись.

Пара описательная: общий хост, фиксированный порядок shared → independent и короткие всплески не дают причинной оценки одной SQL-команды. Синтетические векторы не измеряют качество модели или retrieval recall. Нагрузка не устанавливает производственный SLO, предел пропускной способности, поведение managed PostgreSQL или неограниченной внешней очереди. Default sync и правила допуска модели по этому опыту не меняются.

Следующий инженерный gate — неизвестный исход embedding COMMIT при потере подтверждения: отдельный fault injection после подтверждённой записи, затем restart и проверка единственности индекса/события, отсутствия скрытого replay и отказа старому lease.
