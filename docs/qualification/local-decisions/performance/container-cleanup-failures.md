# Очистка собственных контейнеров после ошибок Docker

28.09.2026. Продолжение [исправления process cleanup](./shadow-cleanup-inventory.md)
в [real Temporal/RAG launcher](../../../../scripts/run-temporal-real-rag.py).

## Воспроизведённый дефект

Прежний общий `try` вокруг listing, цикла удаления и итоговой проверки пропускал
удаление уже известных контейнеров при ошибке listing. Ошибка первого `docker rm`
также прекращала остальные удаления и финальную проверку. После выделения прежнего
блока в функцию без изменения поведения три regression-сценария провалились:
отказ discovery с известными контейнерами, отказ одного удаления и недоступное
повторное наблюдение после discovery failure.

Теперь успешный listing задаёт актуальный список целей; уже удалённые shell
launcher контейнеры повторно не удаляются. Если listing недоступен, остаются
пригодны ранее наблюдавшиеся собственные имена. Каждое удаление и финальное
наблюдение выполняются независимо. Ошибки сохраняются как этап и класс исключения,
без текста Docker diagnostics. Неизвестный итог или оставшийся контейнер означает
неуспешный cleanup даже при формально успешном `rm`. Retry может завершить очистку,
но не стирает ошибки первоначальной попытки.

По [документации Docker](https://docs.docker.com/reference/cli/docker/container/ls/)
фильтр `name` сопоставляет и часть имени. Поэтому и discovery, и fallback требуют
полного соответствия имени двух тестовых launcher и PID из наблюдавшегося
собственного process tree. [Удаление с `--force`](https://docs.docker.com/reference/cli/docker/container/rm/)
применяется отдельно к каждому такому контейнеру. Системная очистка Docker и
удаление контейнеров только по общему префиксу не используются.

## Проверки

[Восемь unit-сценариев](../../../../scripts/test/test_temporal_container_cleanup.py)
проверяют все три отказа, исчезнувшие/новые контейнеры, неверный успех `rm`,
недоступное финальное наблюдение и исключение чужих/частично совпадающих имён.

Opt-in live test проверил discovery/removal/verification failures на трёх наборах
настоящих контейнеров. Каждый набор содержит две цели и один контрольный контейнер
с другим owner PID. Контрольный контейнер продолжает работать после проверяемой
очистки; затем fixture удаляет только созданные ею IDs. В сценарии removal failure
повтор удаляет оставшуюся цель, сохраняя первоначальный failure record.
Все девять контейнеров fixture удалены. Использован локально разрешённый image ID
BusyBox, `--network none`, `--read-only` и `--pull never` при запуске.

Первый opt-in запуск остановился до создания контейнеров: image tag присутствовал
в `docker image ls`, но `docker image inspect` вернул `No such image`.
Журнал сохранён; после явного `docker pull busybox:1.36` полный целевой набор
из 71 проверки прошёл. В CI live test включён отдельным обязательным шагом job `test`.
Прежний verifier дополнительно отвергает подменённый успешный отчёт с ошибкой
Docker discovery или verification.

Полная регрессия: 12 Node tests и 430 Python tests прошли; opt-in Docker test
пропущен в обычном discovery и отдельно пройден выше. Проверены process catalog
и 2116 локальных ссылок в 230 Markdown-файлах. Изменённый CI workflow прошёл
`actionlint`; общий запуск отдельно обнаружил существующий незадекларированный
custom runner label другого workflow. [Checks и SHA исходников/журналов](./evidence/2026-09-28/container-cleanup-failures/checks.json)
сохранены без сырых Docker diagnostics; журналы находятся в `docs/private`.

Runtime profile и Workflow-код не менялись. Эти проверки не являются повторным
MLX benchmark, предметной qualification или установлением причины прежнего ENOSPC.

удаления контейнера: отсутствие самого контейнера ещё не подтверждает отсутствие
