# Явный отказ при несовместимом embedding запроса

26.09.2026. Исправлен дефект в coordinator: **неверная embedding-модель, несовместимая размерность или повреждённый проверяемый вектор больше не превращаются в успешный поиск без источников**. Worker получает ошибку retrieval до вызова primary и shadow. Корректный запрос после ошибки снова возвращает источники.

## Причина и изменение

Ранее поиск отбирал chunks по имени модели, а `cosineSimilarity` возвращал `null` при разных размерностях. Такие кандидаты молча удалялись; пустой `hits` был успешным ответом. Worker мог продолжить генерацию без RAG-контекста, хотя причиной был сломанный embedding-контракт. Повреждённый JSON/нулевой вектор в индексе также пропускался.

[Проверка поиска](../../../../apps/coordinator/src/database.ts) теперь до ранжирования и ограничения числа кандидатов сверяет модель каждой запрошенной коллекции и размерность готовых индексированных chunks. Некорректные metadata, повреждённые векторы среди рассматриваемых кандидатов, расхождение их фактической длины с metadata и нечисловой cosine score приводят к явной ошибке. Запрос остаётся в прежней транзакции: если второй query несовместим, успешное событие retrieval и частичный список источников не записываются.

Совпадение размерности запроса с индексом — обычный контракт vector search, прямо описанный, например, в [официальной документации Pinecone TypeScript SDK](https://sdk.pinecone.io/typescript/documents/data-operations_working-with-vectors.html). Здесь это реализовано в существующем локальном хранилище Агата; внешний vector service не подключался.

Пустой результат допустимого поиска по необязательной пустой коллекции остаётся корректным. Исправление различает отсутствие индексированных документов и несовместимый запрос; оно не вводит оценку семантической достаточности найденных фрагментов. Разные коллекции одной модели могут иметь несовместимые размерности после смены модели за прежним именем: общий worker query теперь выдаст ошибку. Нужно исправить модель/index, а не дополнять или обрезать вектор.

## Проверка поведения

Четыре новые [store-регрессии](../../../../apps/coordinator/test/knowledge-retrieval-validation.test.ts) воспроизвели прежнее поведение до исправления и прошли после него. Они покрывают неверную модель, несовместимые размерности, несколько коллекций/queries, отсутствие частичной записи, повреждённые векторы и восстановление после исправления входа.

[Сквозной тест](../../../../apps/coordinator/test/knowledge-retrieval-workflow.test.ts) использует настоящие временные coordinator, SQLite и Python worker. После успешной индексации двух документов endpoint возвращает для query другую размерность либо HTTP 503. В обоих случаях primary и shadow не вызываются. Контроль с корректными embeddings выполняет все три этапа и три shadow-вызова, сохраняя оба источника. Ответы моделей в этом регрессионном тесте контролируемые; реальная модель заново не запускалась.

| Проверка | Результат |
|---|---|
| Новые регрессии до исправления | 4 ожидаемых failure: ошибки не отклонялись |
| Store и прежние knowledge-проверки после исправления | 8/8 pass |
| Workflow отказа/восстановления и прежние RAG-проверки | 4/4 pass |

[Evidence](./evidence/2026-09-26/retrieval-validation-checks.json) содержит SHA кода, команд и логов. Runtime decider и Python worker не менялись. Свежая PostgreSQL-проверка и нагрузочное измерение дополнительных metadata-запросов на большой коллекции не выполнялись.

До изменения coordinator сохранён [точный архив исходника](./evidence/2026-09-26/rag-before-retrieval-validation.json). [Прежний парный RAG-опыт](./rag-paired.md) повторно [проверен по архиву](./evidence/2026-09-26/paired-rag/verification-after-retrieval-fix.json); новое исправление ему не приписывается.
