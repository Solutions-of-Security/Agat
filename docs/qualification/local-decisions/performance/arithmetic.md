# Арифметический baseline для операционного отчёта

26.09.2026. Добавлен отдельный калькулятор двух структурированных записей и детерминированный Markdown-отчёт. На прежнем [учебном входе workflow](./workflow.fixture.json) он вычисляет среднее **4 → 3 часа, −25%** и долю отклонений **8% → 5%, −3 п.п.**. Проверены девять заранее заданных точных значений. Модель не вызывалась; действующие процессы и их primary-ответы не изменены.

В [трёхэтапном модельном workflow](./workflow.md) именно эти показатели оказались неверными во всех 20 итогах двух опытов. Новый baseline проверяет, какую часть этой задачи можно решать обычным кодом. Он требует явных числовых записей и не заменяет извлечение фактов из произвольных документов.

## Контракт расчёта

[Калькулятор](../../../../scripts/lib/report_arithmetic.py) принимает ровно два периода в порядке «исходный → новый». Для каждого нужны название, source ID, число заявок, часы обработки и число заявок с отклонением. Отклонение учитывается максимум один раз для каждой заявки. Числитель, часы и знаменатель должны относиться к одной и той же совокупности; библиотека не может установить это по самим числам.

[Пример входа](./evidence/2026-09-26/arithmetic-input.json) содержит `schemaVersion: agat.report.operations-input.v1`, SHA исходного текста и две записи. Counts — целые JSON-числа от 0 до миллиарда; Boolean и дробные counts отклоняются. Часы — неотрицательная десятичная **строка** до шести знаков после точки, максимум 10¹². Экспонента, NaN, infinity, десятичная запятая и float вместо строки не принимаются. Число отклонений не превышает число заявок. Ненулевые часы при нуле учтённых заявок отвергаются как несовместимые с данным контрактом.

| Показатель | Формула | Единица изменения |
|---|---|---|
| Количество заявок | Значения двух периодов | Заявки и относительные проценты |
| Общее время | Значения двух периодов | Часы и относительные проценты |
| Среднее время на заявку | Часы / заявки | Часы на заявку и относительные проценты |
| Доля отклонений | Отклонения / заявки × 100 | Процентные пункты; относительное изменение сохранено отдельно |

Все вычисления идут через точные рациональные числа, без промежуточного округления и binary float. Машинный [результат](./evidence/2026-09-26/arithmetic-result.json) хранит числитель/знаменатель как строки, единицу и отдельное округлённое отображение. Для display применяется half-even, 0–6 знаков после точки; по умолчанию 3. Округление не меняет исходные дроби.

Нулевой знаменатель даёт `status: undefined` с причиной и `exact/display: null`. Нулевая исходная величина делает относительный процент неопределённым, даже если абсолютное изменение известно. Среднее и доля при отсутствии заявок не превращаются в 0. Если хотя бы одна величина неопределённа, общий status — `partial`; остальные определённые величины сохраняются.

SHA связывает результат с предоставленными записями и переданным идентификатором источника. Сам калькулятор не читает исходный документ и всегда возвращает `sourceValuesVerified: false`: hash не доказывает корректность извлечения. Qualification и routing также остаются false. Правильная арифметика не устанавливает причины изменений и не подтверждает достоверность исходных данных.

## Проверенный пример

[Инструмент проверки](../../../../scripts/check-report-arithmetic.py) извлекает две записи из существующего **авторского синтетического** fixture по его точному ограниченному формату. До вызова CLI он сохраняет [план](./evidence/2026-09-26/arithmetic-plan.json) с исходными фрагментами/позициями, source/code SHA и девятью ожидаемыми значениями. Это механическое сопоставление известного шаблона, а не NLP-экстрактор для реальных источников.

| Контрольная величина | Точный результат |
|---|---:|
| Прирост заявок | +20% |
| Изменение общего времени | −10% |
| Среднее первого / второго периода | 4 / 3 ч |
| Изменение среднего | −25% |
| Доля первого / второго периода | 8% / 5% |
| Разность долей | −3 п.п. |
| Относительное изменение доли | −37.5% |

[Готовый отчёт](./evidence/2026-09-26/arithmetic-report.md) создан CLI без модели. Перед рендерингом библиотека заново пересчитывает результат и отвергает изменение даже повторно sealed JSON. [Проверка](./evidence/2026-09-26/arithmetic-verification.json) подтвердила все девять значений, единицу `percentage_points`, привязку к записям и правильные строки Markdown. Известные правильные числа были получены ещё при анализе исходного workflow: это regression baseline, не новая независимая выборка.

[11 тестов](../../../../scripts/test/test_report_arithmetic.py) покрывают прежнюю ошибку знаменателя, разницу процентов и процентных пунктов, десятичные и периодические дроби, half-even с отрицательными значениями, нулевую базу, изменение масштаба совокупности, перестановку периодов, границы/типы входа, markup в labels, неизменность входа и подмену результата. На классификацию, source extraction и экспертную оценку эти тесты не претендуют.

## Использование

```bash
python3 scripts/calculate-report-metrics.py \
  --input docs/qualification/local-decisions/performance/evidence/2026-09-26/arithmetic-input.json \
  --output docs/qualification/local-decisions/performance/evidence/new-run/arithmetic-result.json \
  --markdown docs/qualification/local-decisions/performance/evidence/new-run/arithmetic-report.md \
  --decimal-places 3

python3 scripts/check-report-arithmetic.py \
  --fixture docs/qualification/local-decisions/performance/workflow.fixture.json \
  --evidence-dir docs/qualification/local-decisions/performance/evidence/new-run
```

Output должны находиться под `docs` и не существовать. Новые зависимости, модели и серверы не требуются. Runtime модели остаётся `0.12.0`; калькулятор не участвует в его profile SHA.

Для прикладного workflow остаётся отдельная задача: получать такие записи из конкретного источника с проверкой mappings, единиц, совокупности и пропусков, затем использовать вычисленные значения как основу числовой части отчёта. Генеративную формулировку нельзя автоматически считать проверенной только потому, что ей передан правильный расчёт. Шаблон рабочего пакета отчёта и его обязательное человеческое согласование этим baseline не менялись.

[Следующий шаг — CSV с закреплённым SHA и явным mapping](./source-records.md) — реализован: две строки связаны с исходными байтами, колонками и расчётом; поддержаны BOM/CRLF и строгие отказы. Истинность источника и соответствие совокупности остаются непроверенными декларациями, а прикладной процесс ещё не изменён.

Выбор точных дробей основан на [Python Fraction](https://docs.python.org/3/library/fractions.html) и описании [ограничений floating point](https://docs.python.org/3/tutorial/floatingpoint.html). Раздельное представление относительных процентов и процентных пунктов соответствует [пояснению ONS](https://service-manual.ons.gov.uk/content/numbers/percentages). Источники проверены 26.09.2026.
