## Метод

Использован неизменённый [development-набор](../development/evidence/2026-09-26/dataset.json): 15 случаев, каждый повторён четыре раза при конкурентности 1, 2 и 4. Перед измерениями выполнены три отдельных прогрева. Итого 180 измеряемых попыток и три прогрева; holdout и calibration не используются. Загрузка модели не измеряется, состояние прогрева уже запущенного сервера до опыта неизвестно.

Каждая группа запросов стартует через barrier, следующая ждёт завершения предыдущей. Это синхронные всплески с ограниченной конкурентностью, не фиксированная интенсивность production-трафика. Нет скрытого retry, очереди или замены `busy` успешным ответом. Измеряется весь локальный HTTP-вызов worker, включая watchdog и чтение; primary inference и запись coordinator в него не входят.

Профиль фиксируется перед началом, передаётся в каждом запросе и повторно проверяется после прогона. Валидатор проверяет input SHA, identity, logits/softmax, typed Boolean, пороги, abstain и счётчики токенов. Ответ HTTP 200 с неверным содержимым учитывается как ошибка. Gold labels не передаются runtime. Сырые входы не дублируются в отчёте.

|---:|---:|---:|---:|---:|---:|
| 1 | 60/60 | 0 | 249.454 | 382.487 | 3.989 |
| 2 | 30/60 | 30 | 250.124 | 333.369 | 4.021 |
| 4 | 15/60 | 45 | 256.505 | 391.654 | 4.015 |

`ok` и `abstain` здесь оба означают выполненное вычисление. При конкурентности 1 было 32 `ok` и 28 `abstain`; это не подсчёт правильных ответов. Все входы имели 152–591 токен. Ошибок протокола, таймаутов и смены профиля не было. Время трёх прогревов: 498.929, 335.919 и 214.086 мс.

Для одиночных запросов максимальное время — 498.798 мс, 29/60 превысили 250 мс, ни один не превысил 500 мс. Быстрые `busy` имеют отдельный p95: 2.554 мс при конкурентности 2 и 2.974 мс при 4. Их включение в общую задержку искусственно улучшило бы показатели, поэтому они исключены из распределения вычисленных ответов и сохранены в распределении отказов.

Наблюдение соответствует существующему ограничению runtime: один forward за раз, лишние запросы немедленно отклоняются. Увеличение конкурентности не повысило фактическую пропускную способность. Практическое решение для нынешнего shadow: сохранить один запрос на экземпляр и fallback при `busy`; увеличение worker concurrency само по себе не ускоряет decision backend. Пакетирование или несколько GPU-процессов требуют отдельной проверки памяти и эквивалентности результатов.

Это короткий опыт на одном компьютере с повторяющимися входами. Длительные хвосты, другие размеры контекста, загрузка primary-модели на том же GPU, память сервера, cold start и поток с заданной интенсивностью здесь не измерялись. 60 повторов не равны 60 независимым примерам качества. Малый p95 при конкурентности 4 — всего 15 выполненных запросов, то есть максимум этой выборки. Порог 500 мс или 1 с нельзя объявлять production SLO по этому результату.

## Воспроизведение

Сначала запустите runtime из [инструкции shadow](../shadow/README.md), затем из корня проекта:

```bash
python3 scripts/benchmark-local-decisions.py \
  --url http://127.0.0.1:8766 \
  --dataset docs/qualification/local-decisions/development/evidence/2026-09-26/dataset.json \
  --rounds 4 --concurrency 1 2 4 --warmup 3 --timeout-ms 10000 \
  --output docs/qualification/local-decisions/performance/evidence/new-run/decider-http.json

python3 -m unittest scripts.test.test_decision_performance -v
```

Инструмент допускает не более 100 development-случаев, 10 повторов, конкурентность до 8 и 1200 суммарных попыток. Deadline — 100–10 000 мс; существующие evidence-файлы не перезаписываются. `observed` означает, что профиль сохранился и не было ошибок, кроме ожидаемого `busy`; `degraded` возвращает exit code 1 и сохраняет наблюдения. Клиентский таймаут не отменяет уже запущенный Metal forward.

Пять автоматических проверок покрывают разделение задержек и отказов, запрет holdout/Score/избыточного плана до сети, отсутствие gold и исходного текста в отчёте, несовпадение профиля и подмену типизированного ответа. Они включены в `npm run docs:check`, который также прошёл после добавления PostgreSQL-проверки.

Метод следует [Google SRE: latency, traffic, errors, saturation](https://sre.google/sre-book/monitoring-distributed-systems/): успешные и ошибочные ответы измеряются отдельно. Здесь `busy` показывает достижение ограничения обслуживаемых запросов; использование GPU и памяти этим счётчиком не измеряется.

[Расчёт отчётных показателей кодом](./arithmetic.md) проверен на прежнем синтетическом workflow-входе: точные дроби, явные знаменатели, нулевая база и Markdown без генерации. Это отдельный функциональный baseline; новый нагрузочный model benchmark не проводился.

[Привязка расчёта к CSV-источнику](./source-records.md) добавляет проверку SHA, точных ячеек, byte offsets, единиц и явных деклараций совокупности. На прежнем `SUPPORT-DEMO` сверены две строки и девять значений. Проверки фактической достоверности источника и рабочего бизнес-процесса это не заменяет.

[Подготовленный процесс точного отчёта](./source-process.md) добавляет обычное согласование и три скачиваемых артефакта: Markdown, исходный CSV, расчётный JSON. HTTP-проверка подтвердила отсутствие файлов до согласования/после отказа, запрет частичного старта и сохранение SHA после подтверждения. Процесс фиксирует один снимок источника; обновление данных требует новой подготовки.

[Расчёт по отдельным заявкам](./request-records.md) проверяет ключ «период + ID», исключает одинаковые повторы и отклоняет конфликтующие значения. Пример: 6 исходных строк → 4 уникальные пары → точные показатели и процесс с согласованием. 38 Python-проверок и оба HTTP-сценария прошли; реальная полнота и семантика выгрузки требуют проверки владельцем.

[Новые снимки локального CSV](./source-snapshots.md) добавляют стабильное чтение и сравнение с предыдущим bundle. Изменившаяся выгрузка создаёт отдельный проверяемый результат, неизменная — не создаёт новый каталог, конфликтующая — отклоняется. Подготовка остаётся однократной, публикация и решение владельца выполняются отдельно.

[Срок действия retrieval-аренды](./retrieval-lease-validity.md): воспроизведён и исправлен поиск по истёкшему lease до maintenance. SQLite и две реплики PostgreSQL проверяют отказ без записей и восстановление только по новому lease.

[Изолированный исполнитель retrieval](./retrieval-isolated-executor.md): полный поиск в постоянном worker, ограниченная очередь и проверки credentials/lease после ожидания. Парный HTTP-опыт с настоящим maintenance подтвердил 84/84 поиска и меньшие наблюдаемые задержки health. SQLite сохраняет задержки фоновых записей; операторский opt-in PostgreSQL требует учёта pool budget, readiness и конфликтующих изменений.

[Операторский PostgreSQL opt-in](./retrieval-postgres-opt-in.md): подключение в main, разделение прежнего pool budget между main и retrieval, health после остановки, проверка настоящего entry point. Default sync сохранён; нагрузка и восстановление полного coordinator продолжаются отдельно.

[Shutdown с заполненной очередью](./retrieval-shutdown-drain.md): воспроизведение и исправление позднего закрытия admission; heartbeat, lease renewal, main maintenance и restart без replay на настоящем coordinator/PostgreSQL.

[Shutdown с UI/A2A-подписками](./coordinator-stream-shutdown.md): завершение долгоживущих HTTP-ответов без отмены сохранённых tasks, возобновление UI event IDs после restart и отсутствие поздних чтений закрытого store.

[HTTP-профиль обычного main](./retrieval-main-http.md): 42/42 поиска + 2 warmup на одном commit, реальный maintenance и один pool budget. При конкурентности 4 health max 8563 → 78 мс, пропуски health probes 232 → 0; скорость поиска не улучшилась одинаково. Девять replay-тестов включены в CI с доступом к исходным commits.

[Повторная проверка lease перед сохранением](./retrieval-lease-locking.md): поиск отклоняет истечение и отмену во время ожидания; PostgreSQL row locks удерживаются после ranking, чтобы чтение индекса не задерживало продление.

[Deadline при SQL-блокировке служебного HTTP](./retrieval-control-lock-deadline.md): воспроизведена задержка main timer при renew, ожидающем stage активного поиска. Остаток срока передаётся в PostgreSQL statement_timeout; проверены отказ без replay, rollback, cursor cleanup и restart.

[Потеря подтверждения COMMIT](./retrieval-commit-acknowledgement.md): настоящий commit подтверждён отдельным соединением до fault; isolated отдаёт 503/504 и закрывает очередь, sync заменяет повреждённое соединение. Сохранённый `K1` не повторяется; только явный запрос создаёт `K2`.

[Повтор main HTTP после SQL deadline](./retrieval-deadline-http.md): ещё 42/42 поиска и 2 warmup прошли полный replay на одном commit. Isolated health max при конкурентности 4 — 34 мс против 6755 мс в sync, пропусков probes нет; медиана поиска выше во всех сериях. Зафиксированы реальные maintenance, память, штатный exit и удаление контейнеров.

[Срок lease во время записи](./retrieval-lease-write-fence.md): воспроизведено сохранение после expiry при блокировке INSERT retrieval или события. Повторная проверка перед выходом из транзакции откатывает обе записи; проверяется восстановление по новому lease с `K1`.

[Допуск terminal-ответов](./terminal-lease-admission.md) проверен независимо от retrieval и shadow: свежий срок после stage lock, сохранение нового владельца при позднем `/fail`, отказ до записи артефактов и успешный retry.

[Конкурирующий maintenance](./lease-maintenance-locks.md) сохраняет своевременное renewal и принятое завершение, освобождает lease одной из реплик и откатывает SQL-переходы при отказе события.

[Lifecycle embedding lease](./embedding-lease-lifecycle.md): просроченные и переназначенные попытки не продлевают аренду и не меняют индекс; поздняя запись откатывается, maintenance сохраняет согласованность job/document.

[Продление аренды после ожидания SQL](./lease-renewal-deadlines.md) закрывает устаревший cutoff stage renewal и поздний UPDATE stage/embedding; SQL-only продление откатывается при истечении прежнего срока.

[Размерность при конкуренции jobs](./embedding-dimension-concurrency.md) защищает общий embedding-индекс блокировкой коллекции перед job; смешанный индекс [2, 3] воспроизведён и устранён на двух coordinator с положительными контролями.

[HTTP-профиль embedding/renewal](./embedding-http.md): два coordinator, 420 completion + 4 warmup, 13568 проверенных векторов; все health/renewal успешны без пропусков probes. Схемы shared/independent сравнены по фиксированному протоколу без вывода о производственном SLO.

[Потерянное подтверждение embedding COMMIT](./embedding-commit-acknowledgement.md): независимая проверка записи до разрыва/timeout, отказ старому lease, restart без повторной записи и выдача только оставшегося chunk.

[Восстановление настоящего Python worker](./embedding-worker-recovery.md): после потерянного COMMIT-ответа тот же worker завершает остаток и следующий документ; HTTP attempts, завершение renewal threads и точные сохранённые векторы проверяются независимо.

[Отмена после окончательного отказа embedding renewal](./embedding-worker-lease-cancellation.md): HTTP 404 во время model HTTP прекращает renewer и отправку устаревших complete/fail; временные ошибки связи сохраняют нормальное продолжение.

[Ограничение чтения embedding model HTTP](./embedding-http-response-limits.md): успешный JSON до 8 МиБ, error prefix до 4096 байт; два real-worker сценария подтверждают recovery с новой арендой и сохранением только успешного результата.
