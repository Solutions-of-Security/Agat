# Допуск ответа primary по текущему lease

Дата: **27.09.2026**. После [shadow-записи](../shadow/lease-expiry.md) независимо проверены `completeLease` и `failLease` — обработчики успешного завершения и ошибки основного шага.

## Дефекты и исправление

В baseline `0b9a0c7aa9ef1288af68e44fd749d06066e4b006` оба обработчика принимали lease со статусом `running`, не проверяя его срок. До фонового освобождения просроченный ответ мог завершить процесс и записать артефакты либо вернуть шаг в очередь. Кроме того, `failLease` читал строку без `FOR UPDATE`: после конкурентной смены владельца его последующий UPDATE по stage id стирал новый lease.

Теперь оба обработчика сверяют конечную корректную дату со свежим временем **после чтения под блокировкой**. Отказ происходит до переходов процесса, событий, shadow `missing_result`, метрик и файловых/S3 записей. `failLease` получает такую же блокировку строки, какую уже использовал `completeLease`. SQLite опирается на существующую транзакцию `BEGIN IMMEDIATE`. Ошибка сохраняет действующий HTTP 400 и текст «Активная аренда не найдена».

| Реальная конкуренция PostgreSQL | `complete` до → после | `fail` до → после |
|---|---|---|
| Исходный lease истёк во время ожидания | 200 и 3 артефакта → 400, артефактов 0 | 200 и stage `queued` → 400, исходное состояние не меняется этим запросом |
| Владелец и lease заменены другой транзакцией | 400 → 400, новый владелец сохранён | 200, новый владелец потерян → 400, новый владелец сохранён |
| Lease своевременно продлён, старая дата уже прошла | 200 → 200, нормальное завершение | 200 → 200, обычная повторная попытка |

Для каждого опыта запускается настоящий собранный coordinator. Отдельное PostgreSQL-соединение удерживает stage lock и моделирует конкурентную запись. Тест наблюдает ожидаемый SQL в `pg_stat_activity`, удостоверяется, что запрос заблокирован до старого expiry, затем снимает блокировку. При смене владельца новый lease записывается явно как fault fixture; последующее завершение проходит через обычный `completeLease`. После отказа просроченному запросу выдаётся новый lease с учётом действующего model router и завершается primary с тремя ожидаемыми артефактами.

Шесть SQLite-проверок отдельно покрывают обе операции в трёх случаях: `now == expiresAt` до запроса, достижение этой границы после настоящего SELECT и повреждённая дата. До исправления все шесть провалились. После исправления stage, события и дерево файлов остаются неизменны; новая попытка работает.

## Решение и его пределы

[Temporal описывает отказ на поздний ответ задачи](https://docs.temporal.io/troubleshooting/request-failures#not_found-on-respond-operations): сервер может уже считать попытку истёкшей или переназначенной. Для Агат отсюда принято проектное правило: принятие terminal-ответа требует текущего владельца и действующего срока. [PostgreSQL Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html) повторно проверяет условия `SELECT FOR UPDATE` на изменённой строке, что сохраняет нового владельца и позволяет увидеть продлённый срок.

Граница этого этапа — **допуск перед побочными эффектами**. Начавшееся по действительному lease завершение сохраняет существующий путь записи результата. Новый abort после файловой или S3-записи не добавлялся: откат SQL сам по себе не отменяет такой внешний эффект. Это не обещание физического COMMIT или ответа до expiry и не новая exactly-once гарантия для внешних действий.

Фоновое освобождение lease использует отдельный путь чтения и изменения stage. Следующий gate — проверить его гонки с renewal, переназначением и завершением, включая одновременное обслуживание двумя coordinator; нельзя считать его защищённым только потому, что terminal-обработчики теперь проверены.
