# Cleanup shadow runtime при отказе наблюдения

28.09.2026. Исправлен воспроизведённый дефект контроллера и launcher
[полного Temporal/RAG](./temporal-runtime-0.12.1.md): ошибка получения process
inventory больше не мешает остановке уже принадлежащих им процессов.

## Дефект и исправление

Контроллер вызывал inventory и остановку в одном `try`. При `PermissionError`
на системном `ps` выполнение переходило сразу к обработчику ошибки. Родитель
и isolated child продолжали работать, но `closed` становился `true`; повторный
`close()` уже ничего не делал. Такой отказ возник при первой sandbox-проверке
предыдущего этапа; оставшиеся собственные fixture-процессы были идентифицированы
и остановлены отдельно.

Три новые проверки воспроизвели проблему до изменения: готовый runtime,
частично запущенный runtime и ошибка stop callback. Старый код провалил три
сценария и их проверки teardown. Аварийный `finally` самого теста закрыл fixtures.

Теперь наличие `Popen` handle достаточно для обязательной попытки остановки:
root PID записывается до inventory, ошибки наблюдения и остановки учитываются
отдельно, обработка продолжается для остальных принадлежащих контроллеру roots.
`closed` становится истинным только после фактического завершения всех родителей.
При живом процессе повторный `close()` может завершить очистку. Ошибка остаётся
в отчёте после успешного retry и не превращает неудачный опыт в успешный.
Сохраняются только имена классов исключений; тексты ошибок и пути не попадают
в failure record. Первоначальная ошибка control-протокола не заменяется cleanup.

Во внешнем launcher аналогично разделены inventory и остановка обычного decider
и Ollama. Если `ShadowRecoveryControl.close()` сообщает ошибку, известные ему PID
и последний runtime handle всё равно переносятся в итоговый отчёт. Ошибка финального
inventory даёт `remainingOwnedPids: null` и неуспешный результат — отсутствие
наблюдения не считается пустым списком живых процессов.

Обратный порядок закрытия и выполнение остальных cleanup callbacks после ошибки
согласуются с [Python ExitStack](https://docs.python.org/3/library/contextlib.html#contextlib.ExitStack).
Сигнал завершения сам по себе недостаточен: проверяется завершённый `Popen`, как
в [документации subprocess](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.wait).
Контроллер по-прежнему принимает только собственные handles; клиент не задаёт PID.

## Проверки и границы

[Process-control tests](../../../../scripts/test/test_temporal_shadow_control.py)
используют настоящий isolated backend с fixture-моделью. Проверены отказы inventory
до и после readiness, остановка нескольких roots после ошибки, повтор stop,
ошибочный callback без фактического завершения и сохранение признака отказа.
[Launcher tests](../../../../scripts/test/test_temporal_cleanup.py) дополнительно
проверяют закрытие настоящего дерева процессов, отсутствие действий без handle,
ограничение проверки собственными PID и неизвестный итоговый inventory.

62 целевых Temporal/profile/verifier/cleanup проверки прошли. Включены прежние
42 проверки реальных исторических evidence; новый код не переопределяет их
source SHA и не переносит qualification между профилями. Runtime-модули,
модельные настройки и Workflow-код не менялись; повторный MLX inference для
этого исправления не заявляется.

Полная проверка документации: 12 Node и 422 Python tests, 2111 локальных
ссылок в 229 Markdown-файлах, актуальность process catalog — pass.
[Итог проверок и SHA исходников/журналов](./evidence/2026-09-28/shadow-cleanup-inventory/checks.json)
сохранён отдельно; диагностические журналы остаются в `docs/private`.

Следующий gate — независимые попытки cleanup всех собственных контейнеров при
ошибке Docker listing или удаления одного из них. Отсутствие проверки cleanup
не должно позволять объявить такой запуск успешным.
