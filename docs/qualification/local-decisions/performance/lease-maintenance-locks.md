# Конкурирующее освобождение просроченных stage lease

Дата: **27.09.2026**. После [проверки terminal-ответов](./terminal-lease-admission.md) отдельно проверен `cleanupExpiredLeases`, который вызывается фоновым обслуживанием и выдачей новых заданий.

## Подтверждённые отказы

Baseline `69b66246e3a69d90f29ef2a7e72c0d78da94fa18` сначала читал список просроченных stage, а затем изменял строки по id. Самостоятельный maintenance не заключал всю последовательность в транзакцию. Ожидание последующего UPDATE не обновляло ранее принятое решение об истечении lease.

Три сценария на PostgreSQL 17.6 используют настоящие процессы coordinator, их периодическое обслуживание и реальный HTTP. Четвёртая группа проверяет откат при ошибке записи события в SQLite.

| Сценарий | Baseline | После исправления |
|---|---|---|
| Renewal начался до expiry, но удерживал строку до следующего maintenance | Продлённая аренда очищена, stage `queued`, одно лишнее `lease.expired`; health не ответил за 1,5 с | Исходный lease и новый срок сохранены, лишних событий 0, health 200 |
| Primary допущен по живому lease; INSERT события задержан до expiry; вторая реплика обслуживает очередь | `/complete` возвращает 200, но maintenance возвращает завершённый run в `queued`; лишнее событие 1 | Run остаётся `completed`, вывод и три артефакта сохранены, лишних событий 0, health второй реплики 200 |
| Две реплики видят одну просроченную строку под внешней блокировкой | Обе ждут, затем записывают два события истечения | Обе пропускают занятую строку; после освобождения выполняется ровно одно истечение; health 200 у обеих |
| INSERT события отклонён после изменений stage/run: retry и terminal failure | Изменения состояния остаются без события | Изменения stage/run/event откатываются; следующий проход выполняет одну корректную операцию |

В сценарии completion один coordinator действительно обрабатывает HTTP `/complete`, а второй выполняет свой обычный maintenance. SQL-подмена успешного завершения не используется. Тест наблюдает ожидающий INSERT в `pg_stat_activity` до expiry и освобождает его после прохода maintenance второй реплики. В сценарии renewal используется условный UPDATE по ещё действительному сроку и проверяется `rowCount = 1`.

Барьер стенда учитывает обе ситуации: heartbeat после заданного момента либо непосредственно наблюдаемый заблокированный UPDATE stage. Это нужно, потому что heartbeat может записаться за несколько миллисекунд до expiry, а следующий SELECT maintenance уже видит просроченный lease. Первая попытка с одним лишь heartbeat-barrier сохранена отдельно и не засчитана как полное воспроизведение всех трёх гонок.

## Реализация

Выбор просроченных stage и их дальнейшие изменения теперь проходят в существующей транзакции store. PostgreSQL выбирает строки через `FOR UPDATE SKIP LOCKED`; SQLite использует `BEGIN IMMEDIATE`. Блокировки сохраняются до завершения транзакции. Вызов из `leaseNext` использует уже открытую транзакцию, без вложенного BEGIN.

Занятая другой операцией строка пропускается и рассматривается на следующем проходе. После commit конкурентной операции новый SELECT увидит действительное продление, завершённое состояние либо по-прежнему истёкший lease. Две реплики не могут одновременно принять одну строку для освобождения. Отказ записи события откатывает SQL-переходы stage, run и связанные записи процесса вместе.

[PostgreSQL описывает `SKIP LOCKED`](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE) как подход для нескольких обработчиков очереди: занятые строки пропускаются вместо ожидания. Это не полный snapshot для аналитики; maintenance Агат допускает повторный проход, поэтому пропуск здесь уместен. Настройки retry, число попыток, правила compensation и MCP side-effect guard сохранены.

Проверка health ограничена искусственно удерживаемой **строчной** блокировкой. Она не устанавливает production SLO и не обещает отсутствие ожидания table locks, других SQL-операций или внешних сервисов. Атомарность относится к durable SQL-состоянию и событиям; транзакция БД не превращает экспорт OpenTelemetry или сторонние эффекты в откатываемые действия. Полная потеря PostgreSQL primary и рассинхронизация часов здесь не испытывались.
