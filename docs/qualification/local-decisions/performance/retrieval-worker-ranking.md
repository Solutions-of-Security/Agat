# Точный retrieval внутри PostgreSQL-worker

Дата: **27.09.2026**. Статус: реализован и локально проверен. Продолжение [корпусного измерения](./retrieval-corpus.md) и [оценки pgvector](./pgvector-compatibility.md).

## Изменение

PostgreSQL-worker теперь проверяет векторы и выбирает точный topK рядом с транзакционным курсором. Между потоками передаётся один ответ с выбранными metadata и score, без `embedding_json`. Раньше каждая порция по 64 строки сериализовалась и пересылалась coordinator, который заново разбирал все векторы. При 2429 кандидатах это 38 ответов FETCH плюс DECLARE/CLOSE; теперь эти запросы выполняются внутри SQL-worker, а через синхронный мост проходит одна операция ранжирования.

[Общий scorer](../../../../apps/coordinator/src/knowledge-ranking.ts) применяется и к SQLite iterator, и к PostgreSQL cursor. Он сохраняет проверку каждого кандидата, предел 5000, double precision, порядок равных score и округление только после topK. Вектор с ошибкой вне topK по-прежнему отклоняет весь retrieval. Scorer удерживает только лучшие K metadata; размерность, модель, разрешённые collections, lease, provenance и сохранение результатов проверяются прежним путём coordinator.

Новый метод statement — внутренний необязательный accelerator. PostgreSQL требует открытую транзакцию с тем же scope; cursor `WITHOUT HOLD` закрывается при успехе, ошибке данных и SQL-ошибке. При aborted transaction ошибка CLOSE не заменяет исходный отказ FETCH. Схема, роли, формат сохранённых данных и HTTP-контракт не меняются. Старый общий `iterate` остаётся для других запросов и проверок.

Синхронное ожидание coordinator сохраняется: это оптимизация объёма межпоточного обмена, не переход HTTP на неблокирующую обработку. Таймаут SQL-моста теперь ограничивает всю операцию ранжирования одним ожиданием, а не каждый FETCH отдельно. При превышении существующего `connectTimeoutMs + statementTimeoutMs + 5000` (минимум 5000 мс) driver закрывается и завершает worker; частичные hits не сохраняются. Конкурентная нагрузка и восстановление приложения после такого крайнего timeout здесь отдельно не измерены.

## Проверки корректности

Coordinator: **231/231** тест, включая новый float64-контрпример, стабильный порядок ties, отсутствие vector в metadata, ошибку в позднем кандидате, закрытие generator и отказ некорректных options до чтения.

Настоящий PostgreSQL Fleet/HA: **9/9**, без skipped tests. Новый тест синхронизирует две SQL-сессии advisory lock: первая FETCH получает snapshot и ждёт, другая сессия меняет исходную запись и освобождает lock. Победитель в третьей порции сохраняет первоначальный текст, а новый SELECT после COMMIT видит изменение. В тесте нет предположения о задержке запуска Node.

Дополнительно проверены 500 валидных 4096D-векторов (совокупный JSON >32 МиБ), float64 winner после передачи ответа, отказ 5001 кандидата, поздняя SQL-ошибка, rollback, отсутствие открытых cursors, отказ без transaction и RLS чужого проекта. Уже существующая сквозная проверка повреждения позднего RAG-кандидата подтверждает отсутствие частично сохранённых источников и восстановление после исправления.

Полный typecheck всех workspaces и coordinator build прошли. [Команды, результаты и журналы](./evidence/2026-09-27/retrieval-worker-tests/checks.json) отделены от измерительного корпуса.

## Повтор на том же корпусе

Исходники реализации закреплены commit `c1b0d9b`; [план нового опыта](./evidence/2026-09-27/retrieval-worker-ranking/plan.json) записан до измерений и включает SHA всех 12 файлов вычислительного пути. Корпус неизменен: top-level Markdown из `44dbb436f86d8406b8b5713e3e1b66faa7f8a28a`, 66 документов, 2429 embeddings размерности 768, восемь запросов, пять проходов на backend, topK=8. Embeddinggemma и настройки совпадают с [предыдущим опытом после исправления буфера](./evidence/2026-09-27/retrieval-corpus-buffer/plan.json).

[Сверка двух опытов](./evidence/2026-09-27/retrieval-worker-comparison.json) проверяет hash всех файлов manifest, соответствие исходников Git commit, завершение всех шести фаз, выгрузку модели, независимый oracle и точное совпадение всех 80 списков hits. Все 2429 source vectors и восемь query vectors совпадают. Сохранённые имена, digest весов, версия Ollama, details и generation settings тоже совпадают.

Как и в предыдущей паре, **общий hash ответа `/api/show` отличается** (`86f299…` → `602281…`). Полные исходные описания не сохранялись, поэтому причина не установлена. Это явно отражено в comparison; совпадение весов, настроек и самих векторов не заменяется предположением о причине различия.

По 32 warm samples на backend; первый проход записан отдельно. Пик RSS включает весь свежий Node-процесс и worker threads, исключает PostgreSQL server, Docker VM и заранее выгруженную модель. Это одна последовательная пара запусков; причинная оценка без влияния окружения, производственный p95, throughput и семантическое качество не заявляются.

В этом опыте PostgreSQL p50 уменьшился примерно на 19%, p95 на 9%, пик RSS на 37%. Совпадение результатов и снижение обмена подтверждают пригодность изменения для текущего точного backend. Поддерживаемый предел остаётся 5000. Следующий этап — ограниченная проверка больших объёмов и операторского бюджета точного поиска; увеличение лимита требует собственного результата, а не экстраполяции этой таблицы.

## Воспроизведение и cleanup

Команда [launcher](../../../../scripts/run-rag-corpus.py) сохранена в [предыдущем протоколе](./retrieval-corpus.md#воспроизведение-и-ограничения). Для сверки двух уже записанных опытов:

```bash
python3 scripts/compare-rag-corpus.py \
  --before docs/qualification/local-decisions/performance/evidence/2026-09-27/retrieval-corpus-buffer \
  --after docs/qualification/local-decisions/performance/evidence/2026-09-27/retrieval-worker-ranking \
  --before-ref 29c98262602065ea62effef5206b8a96514d3799 \
  --after-ref $(git rev-parse c1b0d9b)
```

Verifier выполняется без `-O/PYTHONOPTIMIZE`; при отключённых assertions он явно отказывает. Он не проверяет исторические PID, которые могли быть переиспользованы ОС. Непосредственно после нового опыта отдельной проверкой подтверждено отсутствие [всех семи дочерних процессов](./evidence/2026-09-27/retrieval-worker-cleanup.json); контейнеров `agat-rag-corpus-*` также не осталось. [Launcher result](./evidence/2026-09-27/retrieval-worker-ranking/launcher-result.json) хранит exit codes и очистку собственного контейнера/тома; [model service](./evidence/2026-09-27/retrieval-worker-ranking/model-service.json) — пустой `/api/ps` до начала retrieval.

Rollback изменения — предыдущая версия приложения: миграции или обратного преобразования данных не требуется. Новый benchmark не закрывает независимую бизнес-qualification, ANN, объёмы выше 5000 или производственные SLO.
