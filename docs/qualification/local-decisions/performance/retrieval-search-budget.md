# Операторский бюджет точного retrieval

Дата: **27.09.2026**. Реализация: `AGAT_KNOWLEDGE_SEARCH_MAX_CANDIDATES`, по умолчанию 5000, допустимый диапазон 1–10000. Продолжение [переноса scorer в SQL-worker](./retrieval-worker-ranking.md). Новый предел является ограничением объёма работы, а не гарантией задержки или production SLO.

## Контракт

Параметр задаётся при запуске coordinator; Compose передаёт его из environment, Kubernetes ConfigMap содержит прежний default 5000. Все replicas одного deployment должны использовать одинаковый бюджет. Для встраиваемого `AgatStore` предусмотрен `knowledgeSearchMaxCandidates`. Схема БД не меняется; operator может вернуть 5000 без преобразования данных.

Допустимы только целые числа в диапазоне. Пустая строка, частично числовая строка, exponent/hex, дробь и выход за пределы вызывают ошибку конфигурации. Worker-запрос содержит только query, collections, модель и topK; добавленное клиентом поле `maxCandidates` не меняет серверный бюджет. Coordinator сам формирует внутренние options ranker и SQL LIMIT `budget + 1`, затем ranker отклоняет превышение. Применённый предел записывается в `queries_json`/trace как `candidateLimit` и входит в hash параметров запроса.

Полный перебор, double precision, проверка всех векторов, стабильные ties, model/dimension checks, RLS, run snapshot коллекций и атомарность retrieval сохраняются. Ошибка второй query не оставляет источники от первой; recovery использует следующий корректный citation marker. PostgreSQL пересылает между потоками только выбранные metadata. SQLite остаётся синхронным iterator. Запрос с восемью queries может потребовать восьми проходов; бюджет не является ограничителем запросов в секунду.

## Заранее выбранный опыт

Исходный корпус остаётся закреплён на `44dbb436f86d8406b8b5713e3e1b66faa7f8a28a`: 66 документов и 2429 уникальных chunks. Для профиля роста launcher принимает `--copies 4`, создавая 264 отдельно названных документа и **9716 кандидатов**. Содержимое повторяется, embeddings считаются для 2429 уникальных chunks и используются повторно. Это синтетический рост объёма реальных embeddings, а не 264 независимых источника и не новое доказательство семантического качества.

До измерения фиксируются: бюджет 10000, dimension 768, topK 8, прежние восемь запросов, пять проходов на SQLite и PostgreSQL, один отдельный Node-процесс search на backend, выгрузка Ollama до retrieval. Python oracle использует полный набор кандидатов и `math.fsum`; допустимые равные score на границе topK не превращаются в ошибку. Все копии имеют отдельные document/chunk IDs и provenance. Временная БД и дочерние процессы принадлежат launcher и очищаются им.

Критерии опыта: 40/40 корректных поисков на backend, по одному retrieval event, корректные markers и provenance, отсутствие пропуска более сильного кандидата, все фазы завершены и cleanup успешен. Latency/RSS записываются как наблюдения без заранее неустановленного SLO. Повышение default не планируется. При отказе опыт сохраняет failure evidence; его нельзя заменить выдуманным успешным измерением.

```bash
python3 scripts/run-rag-corpus.py \
  --source-ref 44dbb436f86d8406b8b5713e3e1b66faa7f8a28a \
  --copies 4 \
  --evidence-dir docs/qualification/local-decisions/performance/evidence/new-scale-run
```

Обычный профиль `--copies 1` сохраняет 5000. Контроль и рост выполнены на одном Node 24.14.0; предыдущие измерения на Node 25 не используются как парный контроль. Все документы и результаты опыта хранятся под `/docs`.

## Наблюдаемый результат

Реализация закреплена до измерений: `d990d721cbaaeb0358475fce3fbfa152753a4731`. [Контроль](./evidence/2026-09-27/retrieval-budget-control/launcher-result.json) и [профиль роста](./evidence/2026-09-27/retrieval-budget-scale/launcher-result.json) завершили все шесть фаз. [Независимая повторная проверка](./evidence/2026-09-27/retrieval-budget-comparison.json) подтвердила 160/160 поисков, хеши всех файлов evidence и 12 исходных файлов, совпадение 2429 исходных и восьми query-векторов. Модель, настройки и hash `/api/show` также совпали.

264 отдельно названных документа действительно проиндексированы как 9716 фрагментов в каждом backend. Каждый размер проверен против собственного полного `math.fsum` oracle; списки hits разных размеров не объявляются одинаковыми, поскольку копии занимают отдельные позиции topK.

| Backend | Кандидатов | Warm p50, мс | Warm p95, мс | Пик RSS процесса, МиБ |
|---|---:|---:|---:|---:|
| SQLite | 2429 | 110,579 | 113,650 | 187,17 |
| SQLite | 9716 | 443,328 | 481,630 | 186,39 |
| PostgreSQL | 2429 | 342,014 | 388,768 | 327,44 |
| PostgreSQL | 9716 | 1332,394 | 1598,795 | 304,03 |

На строку приходится 32 warm-измерения после восьми поисков первого прохода. RSS включает все threads поискового Node-процесса, исключает сервер PostgreSQL, Docker VM и выгруженный Ollama. Более низкий пик RSS большого профиля не считается доказательством уменьшения потребления памяти при росте данных. Машина общая: одновременная пользовательская нагрузка не контролировалась, load average записан в [проверках](./evidence/2026-09-27/retrieval-budget-tests/checks.json) и cleanup. Это один последовательный опыт, без причинной оценки изменения latency и без production SLO.

[Контрольный cleanup](./evidence/2026-09-27/retrieval-budget-control-cleanup.json) и [cleanup роста](./evidence/2026-09-27/retrieval-budget-scale-cleanup.json) проверены сразу после соответствующего запуска: все семь собственных дочерних процессов отсутствовали, временных corpus-контейнеров не осталось.

Повторная проверка сохранённых результатов не запускает модели:

```bash
python3 scripts/compare-rag-corpus.py --growth \
  --before docs/qualification/local-decisions/performance/evidence/2026-09-27/retrieval-budget-control \
  --after docs/qualification/local-decisions/performance/evidence/2026-09-27/retrieval-budget-scale \
  --before-ref d990d721cbaaeb0358475fce3fbfa152753a4731 \
  --after-ref d990d721cbaaeb0358475fce3fbfa152753a4731
```

Режим `--growth` разрешает только объявленное преобразование 1→4: все исходные metadata, content hashes и отдельные имена/URI копий сверяются. Режим обычного сравнения отвергает разные корпуса. Историческое сравнение worker-scorer воспроизводится без изменения результата; одинаковый размер под видом роста, неверная исходная реализация и запуск с `-O` отклоняются.

Следующий этап — конкурентные HTTP-запросы и задержки служебных запросов coordinator. Перенос scorer уменьшил обмен между потоками, но синхронный `Atomics.wait` по-прежнему удерживает основной поток. [Рекомендации Node.js](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop) объясняют, почему это нужно проверять на уровне HTTP, отдельно от времени одного store-вызова. Temporal, бизнес-коннекторы, независимые источники и семантическая qualification этим опытом не закрыты.

## Проверки и границы

Проверяются strict parsing и fail-fast StoreOptions, hard boundary 10000/10001 в общем scorer, полноценный поиск по 6001 фрагменту SQLite/PostgreSQL, отказ default 5000 на том же PostgreSQL, невозможность worker override, atomic rollback и сохранение применённого бюджета. Отдельный PostgreSQL-тест передаёт 10000 синтетических 4096D-векторов (совокупный JSON более 512 МиБ) через cursor и получает правильного позднего победителя через мост всего 1 МиБ.

Перед опытом на Node 24.14.0 прошли 234/234 coordinator-теста, 11/11 Fleet/HA PostgreSQL-тестов, typecheck всех workspace, сборка coordinator и docs check (12 Node + 143 Python теста). [Логи и их SHA-256](./evidence/2026-09-27/retrieval-budget-tests/checks.json) сохранены. Измерение корпуса выполнено после фиксации реализации в Git.

Первые локальные прогоны в синхронизируемой папке Documents не считаются успешными: наблюдались ошибки импорта AWS SDK и длительное ожидание чтения файлов. Ошибка импорта воспроизвелась отдельно от Agat на Node 25 и 24; проверка retry-модуля с tarball закреплённой версии 3.33.3 прошла. Затем `stat` показал `compressed,dataless` у одного из файлов проекта, а стек Git ожидал `mmap` этого файла. [Apple TN3150](https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files) описывает восстановление содержимого dataless-файлов при доступе. Это подтверждает проблему доступности файлов, но не доказывает конкретную причину каждого сбоя импорта.

Для повторной проверки использована локальная копия вне Documents: база Git сверена с исходной, 16 изменённых файлов перенесены с SHA-256 проверкой, выполнен `npm ci` по неизменному lockfile. Он завершился за 6 секунд, после чего все перечисленные проверки прошли. Системные настройки синхронизации и версии зависимостей не менялись. [Контракт npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) предусматривает чистую установку без изменения package-lock.
