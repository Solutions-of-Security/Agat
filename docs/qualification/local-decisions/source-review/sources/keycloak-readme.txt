# Keycloak + GitOps в Агате

## Текущее состояние (AS-IS)

Статус на 19 сентября 2026: подготовка агентов и процесса. Этот пакет не означает, что Keycloak уже развёрнут. Облако, кластер и Git-репозиторий пользователь ещё не выбрал. Неизвестные значения остаются обязательными параметрами; они не заменены вымышленными адресами или доступами.

В основном проекте локального Агата созданы шесть агентов и неопубликованный процесс из 28 шагов. Сохранение подтверждено чтением API и интерфейсом; повторная установка не создаёт дублей. В проекте нет MCP-серверов, а запущенный runtime не поддерживает обязательные ограничения инструментов этого пакета. Подробные результаты находятся в [verification.json](verification.json).

## Результат и границы

Цель процесса: установленный Keycloak с проверенными OIDC/RBAC, декларативной конфигурацией и работающим независимо от Агата GitOps. Шесть агентов выполняют последовательные этапы; решения оператора, ожидание evidence, таймауты и артефакты принадлежат runtime Агата. Локальная доступная модель — `qwen3.5:4b`, runtime `langgraph/tool_loop_v1`; её качество для этой задачи ещё не проверено.

Пакет подготавливает установку в **существующий Kubernetes**. Создание кластера, облачных учётных записей, регистрация домена и выбор платного тарифа находятся за границей этой версии. При отсутствии инфраструктуры первый агент формирует перечень зависимостей. Собственный Keycloak Агата, `master`, существующие пользователи и данные не являются целью изменений.

Канонический источник определений — [генератор пакета](../../scripts/keycloak-gitops-pack.mjs). JSON ниже — его экспорт. Реальные ID и результат чтения из API находятся в [installation.json](installation.json) и [process.installed.json](process.installed.json). Экспорт содержит полные будущие ограничения, а установленный черновик отражает возможности запущенного runtime.

## Агенты и этапы

| Агент | Задача | Что разрешено |
|---|---|---|
| KC · Архитектор требований | Паспорт, минимальные требования, критерии приёмки | Валидация и предложения |
| KC · Инфраструктурный проверяющий | Проверка Kubernetes, БД, DNS/TLS и доступов | Чтение состояния |
| KC · Специалист Keycloak | Realms, clients, роли, MFA, обновление конфигурации | Подготовка плана и файлов |
| KC · GitOps-инженер | Репозиторий, MR, Argo Application, policy checks | Ограниченная запись ветки/MR через gateway, без merge |
| KC · Оператор развёртывания | Применение согласованной ревизии | Только закреплённый SHA после решений Агата |
| KC · SRE-приёмка | OIDC/RBAC, GitOps/drift, идемпотентность, recovery | Проверки и заранее разрешённые тестовые объекты |

Порядок: требования → решение по требованиям → проверка среды → `kc.environment.verified` → конфигурация → Git-изменение → `kc.change.verified` → решение по конкретному diff/SHA → развёртывание → `kc.release.verified` → приёмочные тесты → `kc.acceptance.verified` → принятие результата → акт.

Четыре `signal`-шага принимают evidence доверенного интеграционного сервиса, а не заявления агента об успехе. При отсутствии сигнала ожидание завершается по таймауту: 1 час для environment/change, 2 часа для release/acceptance. Отклонение решения или ошибка этапа завершают процесс без итогового акта. Агентам не выдаётся инструмент отправки этих сигналов.

## Минимальные требования

В Агате откройте **Процессы → Keycloak + GitOps → Входные данные**. Поле уже заполнено [текстом заявки](input.prompt.md): замените `<ЗАПОЛНИТЬ: ...>` и `null`, затем проверьте значения по умолчанию. Указаны Kubernetes, DNS/TLS, PostgreSQL, Git/Argo CD, версии, ресурсы, realm/clients и критерии приёмки; для доступов используются ссылки на секреты. Шаблон можно изменить в стартовом шаге **«Требования к Keycloak» → Параметры → Шаблон входных данных**. Изменения в окне запуска относятся только к текущему вводу; постоянный шаблон редактируется в стартовом шаге. Предпросмотр доступен у черновика, сам запуск остаётся недоступен до публикации и выполнения перечисленных ниже предпосылок.

До запуска заполнить [input.template.json](input.template.json) и проверить по [requirements.schema.json](requirements.schema.json). `null` в шаблоне означает отсутствующий обязательный параметр; шаблон намеренно не проходит валидацию.

- `requestId`, владелец, `pilot` либо `production-ha`.
- Реальный cluster reference, отдельный namespace, hostname, ingress class, TLS и credential refs.
- Закреплённые совместимые версии Keycloak, Operator, configuration CLI и Argo CD. На этапе планирования дополнительно фиксируются image digests; `latest` не допускается.
- Постоянная PostgreSQL с TLS, secret refs, backup destination и заданными RPO/RTO. Совместимость версии БД проверяется перед изменениями.
- Git repository/branch/path и credential ref; готовый Argo CD и ограниченный AppProject. Если их нет, сначала выполняются инфраструктурные подготовительные работы.
- Реальные realms/clients, точные HTTPS redirect URI, роли и тестовый OIDC callback.
- Нагрузка, предел p95/error rate и secret ref тестовой учётной записи. Секреты, kubeconfig и токены в JSON запрещены.

Предлагаемые **стартовые бюджеты пилота**, не универсальные минимумы производителя: 1 pod Keycloak, request 1 CPU / 2 GiB RAM, limit 2 CPU / 3 GiB. Для production-ha — минимум 2 таких pod на разных узлах, HA PostgreSQL и подтверждённая достаточность под целевой нагрузкой. Ресурсы БД, Kubernetes, Argo CD, мониторинга и Агата считаются отдельно. Само количество pod не доказывает отказоустойчивость.

```sh
node scripts/validate-keycloak-request.mjs /absolute/path/to/filled-request.json
```

Валидация JSON не проверяет доступность среды: это отдельная обязанность интеграционного сервиса. Не вставляйте параметры облака или секреты в запрос ради прохождения проверки.

## GitOps и конфигурация Keycloak

Базовая схема: официальный Keycloak Operator, внешняя постоянная PostgreSQL, Argo CD и ссылки на секреты через External Secrets либо согласованный эквивалент. Git хранит desired state; данные пользователей и значения секретов хранятся в предназначенных для этого системах.

Предлагаемая структура целевого репозитория:

```text
infrastructure/keycloak/base/
environments/<environment>/keycloak/
configuration/keycloak/
docs/keycloak/operations.md
docs/keycloak/upgrade.md
docs/keycloak/recovery.md
docs/keycloak/acceptance.md
```

Для текущей схемы выбран `keycloak-config-cli` как кандидат механизма применения realm/client/role configuration. Перед первым apply требуется проверить совместимость закреплённой версии и обновление уже существующего realm. Job запускается при изменениях и регулярно для reconciliation; drift test обязан доказать восстановление управляемого поля. Один startup import или Argo `Synced` этого не доказывает. Удаление unmanaged ресурсов, пользователей, базы и PVC запрещено. Изменяемые поля и их владельцы фиксируются явно, чтобы контроллеры и ручное администрирование не перезаписывали друг друга.

Argo `selfHeal` включается для согласованного желаемого состояния; автоматическое удаление объектов с данными не включается. Миграция схемы БД не откатывается простым Git revert: recovery требует совместимых версий и проверенного backup/restore.

## Интеграции и граница полномочий

[integration-contract.json](integration-contract.json) — **требуемый контракт**, не реализованный и не подключённый MCP-сервер. В обследованном проекте Агата MCP-серверов нет. Не зарегистрированы фиктивные endpoints, tokens или tools.

Нужны 8 инструментов namespace `kcops`: `validate_request`, `inspect_environment`, `plan_configuration`, `prepare_gitops_change`, `validate_change`, `get_operation`, `apply_release`, `verify_release`. Внешний адаптер должен реализовать schema validation, действительные обращения к Kubernetes/Git/Argo/Keycloak, machine checks и отправку evidence. Его реализация и настройка потребуют выбранных целевых систем и ограниченных доступов.

Разрешения проверяются вне модели: project/lease policy Агата плюс сервер инструментов, который ограничивает target, namespace, repo/path и фазу. `apply_release` сверяет фактическое решение Агата с неизменяемыми target/diff/SHA. Поле `approved=true` от модели не является разрешением. Нельзя считать перечень инструментов в prompt достаточным разграничением прав.

Сервис сохраняет operation ID до записи, использует стабильный idempotency key между попытками worker и после timeout сначала сверяет состояние. Неизвестный или частичный результат не превращается в PASS. При неуспехе сохраняется диагностический отчёт, соответствующий instance отменяется/завершается с ошибкой; данные не удаляются автоматически.

Evidence привязывается к конкретным process ID, instance ID, request ID, target, fingerprint и Git SHA. Сервис проверяет обязательные тесты и только затем отправляет соответствующий verified signal. Результат ранней доставки нельзя терять: сервис ждёт готовности нужного signal-step и повторяет доставку сохранённого evidence, не повторяя развёртывание. Отправку сигналов и end-to-end проверки адаптера нужно проверить до публикации процесса.

## Установка определений и публикация

```sh
node scripts/keycloak-gitops-pack.mjs --export
node scripts/install-keycloak-gitops.mjs --install
```

Установщик использует существующий токен локального Агата из `.env` в памяти, не печатает его и не сохраняет в документах. Он создаёт 6 агентов и один **неопубликованный** процесс в основном проекте. Повторный запуск сверяет определения, сохраняет ID и не создаёт дублей; конфликт с изменённым пользователем объектом приводит к ошибке, а не к перезаписи. Установщик не вызывает publish/start, не меняет MCP policy и не развёртывает инфраструктуру.

Выявлено при подготовке: локальный работающий контейнер Агата не содержит `requiredTools`, `mcpToolAllowlist`, `allowPartialStart` и scenario preflight, хотя эти возможности уже присутствуют в рабочем дереве исходников. Чужие незавершённые изменения приложения не развёртывались. Поэтому процесс сохраняется черновиком. Публикация требует:

1. Проверенной версии runtime с сохранением и backend enforcement трёх ограничений; `allowPartialStart: false`.
2. Повторного сохранения полного графа из `process.template.json` с реальными ID шести агентов. Старый API удаляет неизвестные поля графа; они не считаются действующими.
3. Реального MCP-адаптера по контракту, ограниченных credentials и проверенных решений на запись; scope тестовых объектов задан заранее.
4. Валидации заполненных требований и готовности Kubernetes/Git/БД/DNS/TLS/Argo.
5. Проверок отказа, повторного вызова и чужого/повторного evidence; ни unknown, ни skipped не выпускают verified signal.
6. Пилотного запуска с настоящей моделью и настоящими инфраструктурными проверками. Только после него можно говорить о подтверждённом сценарии.

## Критерии приёмки

| Проверка | Условие PASS |
|---|---|
| Развёртывание | Keycloak Ready, Argo Synced/Healthy, совпадают target и Git SHA |
| Вход | Реальный Authorization Code + PKCE, проверенные issuer/audience/signature, refresh/logout |
| Права | Нужная роль разрешена, лишняя роль/чужой ресурс запрещены |
| GitOps конфигурации | Изменение управляемого client/role из Git применено; drift исправлен без Агата |
| Повторный apply | Нет дублей и повторной побочной операции |
| Данные | После рестарта настройки сохранились; backup восстановлен на изолированном стенде |
| Production-ha | Выполнены load/failover тесты по заданным целям, подтверждён HA базы |
| Эксплуатация | В Git `/docs/keycloak` есть runbooks, владелец, ссылки мониторинга/backup и ограничения |

## Источники и проверка

Архитектурный выбор подготовлен по официальным источникам, проверенным 19 сентября 2026; точные версии совместимости ещё не выбраны:

- [Keycloak: basic Operator deployment](https://www.keycloak.org/operator/basic-deployment) — зависимости БД, hostname, TLS; оператор сам БД не создаёт.
- [Keycloak: production configuration](https://www.keycloak.org/server/configuration-production) — production mode, TLS и эксплуатационные зависимости.
- [Keycloak: container resources](https://www.keycloak.org/server/containers) — ориентир памяти небольшого production deployment; профиль выше является предложением проекта.
- [Keycloak: realm import](https://www.keycloak.org/operator/realm-import) — импорт не обновляет существующий realm.
- [keycloak-config-cli](https://github.com/adorsys/keycloak-config-cli) — кандидат применения конфигурации; требуется версия и qualification.
- [Argo CD automated sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/) — reconciliation, self-healing и явная настройка prune.
- [Процессы Агата](../processes.md), [MCP gateway](../mcp-gateway.md), [scenario preflight](../scenario-preflight.md) — возможности исходников; наличие в работающем контейнере проверяется отдельно.

Проверки пакета:

```sh
node --import tsx --test docs/tests/keycloak-gitops.test.ts
```

Тесты структуры, схемы входа и остановок workflow используют временную БД и контролируемые ответы исполнителя. Они не являются тестами настоящего Keycloak, качества модели или развёртывания в Kubernetes. Результаты установки и проверки сохраняются в этом каталоге без секретов.
