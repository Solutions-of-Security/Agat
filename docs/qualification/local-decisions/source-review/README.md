## Что считать реальным

Исходные материалы получены из двух существующих GitHub-заявок и семи файлов проекта: roadmap, протоколы запусков и записи о найденных проблемах. Фрагменты не выдуманы и не переписаны; сохранены снимки, SHA-256, номера строк либо JSON Pointer. Исторические записи описывают состояние на свои даты, а не текущую доступность стенда.

**Только два случая классификации воспроизводят исходные заявки.** Остальные 22 — задания, сформулированные ассистентом по реальным документам. Проверяемые утверждения, действия и перечни обязательных сведений созданы для оценки; они не выдаются за сообщения пользователей или за события эксплуатации. Протоколы реального исполнения на синтетическом handbook/отчёте сохраняют эту оговорку. Производственные данные заказчиков из них не получаются.

`provenance.kind: real` означает происхождение источника. Для каждого случая `taskOrigin` и описание в `provenance.reference` уточняют, была ли это исходная заявка или созданное задание. Этот пакет не доказывает представительность реальной очереди Агат.

## Как получить экспертный набор

Два рецензента независимо работают с отдельными копиями blank JSON v2 и [заданиями v2](./review-tasks.v2.md). Для каждой записи они выбирают `expectedOptionId`, пишут `rationale`, указывают свой `reviewerId` и фактический `reviewedAt`. Для спорных случаев предусмотрен третий рецензент. Подробная процедура — в [руководстве v2](./review-guide.v2.md).

Когда оба review действительно выполнены, из корня проекта:

```bash
python3 -m decision_runtime finalize-review \
  --first docs/qualification/local-decisions/source-review/review.first.completed.v2.json \
  --second docs/qualification/local-decisions/source-review/review.second.completed.v2.json \
  --output docs/qualification/local-decisions/source-review/reviewed.dataset.v2.json
```

Заполненные review и итоговый `expert-reviewed` dataset сейчас **не создавались**. Ассистент не подписывается за рецензентов. Команда с текущими blank-пакетами должна завершиться ошибкой незаполненной разметки.

Seed `agat-source-review-2026-09-26-v1` фиксирован в пакетах и не подбирался по качеству модели. Предварительное распределение пяти групп сейчас даёт 15 development и 9 holdout случаев, **calibration-групп нет**. Это явно видно в readiness-файле. Не нужно менять seed ради прохождения проверки: для предметного испытания корпус предстоит расширить новыми независимыми источниками и реальными заявками, включая запросы доступа. Даже после экспертного просмотра нынешних 24 случаев команда `freeze` не сможет сформировать полный эксперимент без calibration split.

Схемы классификации и уточнения определены для этих заданий. Для уточнения оценивается достаточность именно перечисленных входных сведений, а не универсальное правило «проект и период отчёта». Температура из предыдущего синтетического smoke на эти новые схемы не переносится.

После утверждения v2 выполнен [development-прогон runtime 0.3.0](../development/README.md): только 15 случаев, заранее назначенных в development, оценены decider и Qwen Base в двух порядках вариантов. Девять holdout-случаев моделям не передавались; исходные pool, approved-метки и blank-пакеты сохранены без изменений. Обучение и предметная квалификация не запускались. Новые результаты не меняют статус `awaiting_independent_human_review`.

## Проверка воспроизводимости

### Расширение v3: 48 случаев, без новых экспертных меток

Поиск `repo:Solutions-of-Security/Agat is:issue` 26.09.2026 вернул только прежние #2 и #3. Новых наблюдавшихся заявок, включая выдачу/отзыв доступа, в этом источнике не найдено.

До написания новых меток закреплён [план сбора v3](./acquisition-plan.v3.json): шесть документов из commit `63bd93d8fa847cf268a86c6ad590a8165dfd0eed`, SHA снимков и группы по подсистемам. Это A2A, изолированные инструменты, prompt/eval registry, RAG/memory, Model Router и worker attestation. Сохранены [15 снимков источников](./sources.v3.json), прежние девять не менялись.

В [pool v3](./pool.v3.json) первые 24 запроса, группы, схемы и порядок вариантов побайтно воспроизводят v2. Новые 24 случая — 18 проверок утверждений и шесть проверок достаточности сведений по документации. Все они **авторские задания**, а не реальные обращения пользователей или записи production-исполнения. Они проверяют отрицания, отсутствие замеров и конкретных настроек, отличие справочной операции от изменения работающей системы.

Для работы рецензентов: [задания без меток](./review-tasks.v3.md), [руководство](./review-guide.v3.md), [первый blank-пакет](./review.first.blank.v3.json), [второй](./review.second.blank.v3.json). Отдельно хранятся [черновые предложения](./draft-annotations.v3.md), [машинные метки `assistant-draft`](./draft-labels.v3.json), [описания заданий](./case-specs.v3.json), [точные привязки фрагментов](./source-bindings.v3.json) и [готовность](./readiness.v3.json). Expert IDs и timestamps остаются пустыми, предсказания моделей на новых случаях не получались.

Существующий seed сохранён. Для 11 групп он даёт **35 development, 0 calibration и 13 holdout** случаев. Пять из шести новых групп попали в development, одна — в holdout. Группы или seed после этого не переименовывались и не подбирались для заполнения calibration. Группировка по подсистемам уменьшает пересечение связанных фрагментов, но не доказывает независимость и представительность production-выборки. Ограничения — отсутствие calibration-групп, реальных access-заявок и человеческих review — остаются открытыми.

Выбор такой процедуры опирается на [разделение связанных наблюдений по группам в scikit-learn](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data) и [Datasheets for Datasets](https://arxiv.org/abs/1803.09010): происхождение, способ подготовки, состав и ограничения набора записываются явно. Это методическая основа, а не доказательство качества нового корпуса.

Три автоматических теста сверяют восстановление v1/v2/v3, неизменность старых inputs/splits, пустые review и отказ при подмене seed, исходного задания, снимка или закреплённой группы. `finalize-review` с blank-пакетами по-прежнему отказывает. Новое расширение не заменяет датасет уже выполненного development-сравнения.

```bash
python3 docs/qualification/local-decisions/source-review/build.py --revision v3 --check
python3 docs/qualification/local-decisions/source-review/build.py --revision v2 --check
python3 docs/qualification/local-decisions/source-review/build.py --revision v1 --check
python3 -m unittest scripts.test.test_source_expansion -v
npm run docs:links:check
```

[Генератор](./build.py) проверяет все SHA снимков и точность извлечения, затем побайтно сравнивает восемь производных файлов выбранной версии с восстановленными результатами. Проверяются контракты всех запросов, fingerprint каждого входа, допустимость предложенных меток, соответствие двух repository labels, пустота независимых review и отсутствие экспертных подписей. Для v3 дополнительно проверяются план сбора, сохранность первых 24 случаев и отсутствие утечки source/state между splits. `--write` создаёт производные файлы только в новом комплекте и отказывается перезаписывать существующие. Без `--revision` сохраняется исторический default v1. Утверждённые метки проверяются отдельно по SHA ревью и привязкам v2.

Эта проверка подтверждает целостность и происхождение, а не правильность предметной разметки. Семантические решения проверяются рецензентами по источникам. Процедура калибровки после подготовки достаточного корпуса: [второй этап runtime](../calibration/README.md).

Историческая перепроверка v1 от 26.09.2026: восстановлены все восемь производных файлов, сверены девять снимков и 24 уникальных входа. [Протокол отрицательных проверок v1](./verification.v1.json) подтверждает, что пустые review отклоняются с exit code 1 без создания dataset, а отсутствие calibration split блокирует фиксацию эксперимента. Результаты исправления и текущей проверки v2 сохранены в [отдельном протоколе](./research-review-verification.v2.json).

Дополнительный [расчёт объёма независимых групп](./sampling-plan.md) по примерным критериям показывает: даже при нуле ошибок нужно 437 принятых групп на каждое семейство; в v3 только четыре потенциальные holdout-группы и нет calibration-групп. Расчёт не меняет seed и не использует предсказания модели.
