# Score в shadow lease: числовой контракт v2

26.09.2026. Runtime `0.5.0`, capability `local_decision_shadow_v2`. Только наблюдение: основной агент сохраняет результат и маршрут.

## Представление и смысл

Score использует 2–10 уровней с уникальными ID, описаниями и конечными числовыми значениями в диапазоне −1 000 000…1 000 000. Boolean, строки и повторяющиеся значения отклоняются; `abstain: true` для отдельного уровня не разрешён. Числа имеют семантику IEEE 754 binary64, а не произвольной десятичной точности. Нулевые значения обоих знаков эквивалентны.

Код вычисляет `value = Σ probability[i] × level[i]`. Вероятность и margin для policy относятся к варианту с наибольшей вероятностью. Если он не проходит пороги, возвращается `abstain` и `value: null`, распределение сохраняется. Пройденный порог не доказывает качество шкалы или модели. Для порядковых категорий, где расстояния не допускают усреднение, нужен Choice.

## Fingerprint

Новый Score-запрос содержит `inputFingerprintVersion: "binary64-v1"`. Поле включено в хешируемые данные и отделяет контракт от прежней Python-сериализации. Wire schema остаётся `agat.decision.v1`.

Алгоритм после строгого разбора запроса:

1. Добавить `abstain: false`, если оно отсутствует; нормализовать `-0` в `0`.
2. Удалить только `id` запроса. Сохранить вопрос, состояние, порядок вариантов, описания и версию fingerprint.
3. В копии для hashing заменить каждое числовое `options[i].value` объектом `{"float64be":"<16 lowercase hex digits>"}` — восемь байтов IEEE 754 binary64 в big-endian порядке.
4. Сериализовать без пробелов с сортировкой ключей, обычными JSON escaping строк и UTF-8 без Unicode normalization. Все ключи данного контракта фиксированы и состоят из ASCII; пользовательские строки остаются значениями.
5. Вычислить SHA-256 байтов этой сериализации.

Например, `0` становится `0000000000000000`, `1` — `3ff0000000000000`, `1e-7` — `3e7ad7f29abcaf48`. В самом HTTP-запросе и сохранённой конфигурации значения остаются числами. Двоичное представление нужно только для fingerprint, оно не передаётся модели вместо описаний.

`schemaSha256`, применяемый для области калибровки, использует ту же копию, дополнительно удаляет `state` и сортирует варианты по ID. Перестановка меняет input hash, но сохраняет schema hash. Изменение уровня, вопроса, описания или версии меняет соответствующую идентичность. Запрос без нового поля сохраняет прежний алгоритм; старые evidence и calibration-файлы не переписываются.

Основание выбора: [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html) объясняет необходимость единого представления при hashing JSON и опирается на ECMAScript-сериализацию чисел. В stdlib Python она не совпадает с `JSON.stringify` для целых float, экспонент и отрицательного нуля. В этом узком контракте использованы стандартные [Python `struct` с `!d`](https://docs.python.org/3/library/struct.html) и [Node `writeDoubleBE`](https://nodejs.org/api/buffer.html#bufwritedoublebevalue-offset). Это специальный версионированный fingerprint типизированного запроса, **не реализация JCS/RFC 8785**. Общее изменение сериализатора повредило бы ранее закреплённые артефакты; ручной перенос всех правил ECMAScript добавил бы ненужную поверхность ошибок.

## Профиль, совместимость и проверка ответа

Runtime объявляет `inputFingerprintVersions: ["python-json-v1", "binary64-v1"]` внутри закреплённого `profileJson` и каждого ответа. Новый Score-ответ также повторяет выбранную `inputFingerprintVersion`. Coordinator требует это объявление до публикации Score-конфигурации и проверяет его вместе с model/policy/calibration identity. Смена runtime требует заново получить и проверить точный профиль из `/health`.

| Worker capability | Choice/Boolean lease v1 | Score lease v2 |
|---|---|---|
| Нет capability | `unsupported_worker`, основной шаг продолжается | То же |
| `local_decision_shadow_v1` | Поддерживается | `unsupported_worker`, основной шаг продолжается |
| `local_decision_shadow_v2` | Поддерживается | Поддерживается |

Новый worker принимает оба профиля. Старые Choice/Boolean profiles runtime без поля `inputFingerprintVersions` остаются валидными; coordinator не добавляет новое поле в их запросы. Runtime прежней версии не принимается для нового Score. Нет неявного понижения Score до Choice.

Coordinator независимо пересчитывает hash, softmax, победителя, пороги и взвешенное среднее. Сравнение числового результата допускает только погрешность binary64: максимум из `8 × n × Number.MIN_VALUE` и `8 × n × Number.EPSILON × Σ |p[i] × level[i]|`. Граница зависит от масштаба шкалы; постоянный допуск вроде `1e-6` ошибочно разрешил бы подмену очень малых значений. Сумма модулей учитывает потерю точности при взаимном сокращении положительных и отрицательных слагаемых. Нечисловой `false` не равен Score `0`.

Проверки охватывают дроби, соседние binary64, экспоненты, отрицательный ноль, subnormal, крайние допустимые уровни, неверные версии, подмену среднего и отсутствие capability. Сквозной HTTP-тест использует настоящий Python worker и тестовый backend. [Числовой пример](../request.score.example.json) — интеграционная проверка; арифметику наличия документов в настоящем процессе следует проверять кодом.

В UI отображаются «Среднее по шкале», числовые уровни, полный список вероятностей и вопрос. Поле `selectedProbability` по-прежнему означает вероятность выбранного варианта, а не вероятность правильности среднего.

Реальный [MLX/worker/coordinator smoke](./evidence/2026-09-26/real-mlx-score-v2.json) и [протокол регрессий](./evidence/2026-09-26/verification-score-v2.json) завершились без ошибок. Это подтверждение реализации контракта, не предметная qualification Score.
