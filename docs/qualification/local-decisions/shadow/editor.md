# Настройка локальной проверки в редакторе процесса

Дата: **27.09.2026**. В настройках агентного шага появилась форма Choice, Boolean и Score. Она сохраняет существующий `config.decisionShadow` через обычный API черновиков и опубликованных версий. Локальная модель оценивает **вход шага**; основной агент по-прежнему определяет результат и маршрут.

## Использование

1. Откройте процесс, выберите агентный шаг и нажмите «Настроить проверку».
2. Выберите тип, задайте вопрос, точную строку `profileJson` из `/health` установленного локального runtime и ожидание 100–10 000 мс.
3. Для Boolean задайте два разных описания и значения «Да»/«Нет». Для Choice задайте 2–10 вариантов, при необходимости отметьте отказ от оценки. Для Score задайте 2–10 разных конечных чисел в пределах ±1 000 000 и осмысленные описания уровней. Профиль Score должен объявлять `binary64-v1`.
4. Нажмите «Применить к шагу», дождитесь сохранения черновика и опубликуйте процесс. Для следующей версии используется кнопка «Новая версия».

Настройка требует [включения shadow на coordinator и подключения локального runtime к worker](./README.md#включение). Форма не запускает модель и не меняет её профиль. Отказ от оценки — сохранённое наблюдение; он сам по себе не создаёт согласование и не меняет маршрут.

«Отмена», Escape и закрытие диалога отбрасывают правки формы. «Убрать проверку» изменяет черновик; опубликованные версии и активные запуски сохраняют свои настройки. Остальные параметры агента, включая обязательное подтверждение оператора, редактор сохраняет.

## Контракт и решения реализации

Форма проверяет обязательные поля, Unicode/размеры, диапазон ожидания, число вариантов, уникальность кодов/описаний/значений и доступность числового fingerprint в профиле. Коды ASCII сохраняются без переименования, перестановка вариантов меняет именно их порядок. Boolean `false` остаётся значением; `-0` Score нормализуется в `0`; Choice не получает скрытых числовых значений. Смена типа явно сбрасывает список вариантов, но сохраняет вопрос, профиль и ожидание.

`profileJson` проверяется через JSON parser, но **не сериализуется заново**: пробелы, порядок ключей и `1.0` остаются прежними. Полную проверку model/policy/calibration и pinned SHA выполняет существующий серверный normalizer. Проверка формы не доказывает наличие модели или совпадение профиля запущенного runtime. Ошибка серверной проверки показывается штатным механизмом сохранения процесса; недопустимая версия не публикуется.

Черновик формы отделён от автосохранения графа. Он создаётся при открытии диалога и меняется обработчиками событий; ключ процесса/узла исключает перенос состояния между шагами. Это согласуется с рекомендациями React о [сбросе состояния](https://react.dev/learn/preserving-and-resetting-state) и [управляемом textarea](https://react.dev/reference/react-dom/components/textarea). Нативный modal dialog вынесен через [portal](https://react.dev/reference/react-dom/createPortal) из DOM боковой панели, чтобы не наследовать её размеры текста и мобильное позиционирование. Существующий focus hook удерживает Tab внутри диалога, поддерживает Escape и возвращает фокус на кнопку открытия. Подписи полей связаны через стабильные ID, включая перестановку вариантов.

API, coordinator, worker и формат сохранённого `decisionShadow` не изменялись. Автоматическая маршрутизация не добавлена; `mode` всегда `shadow`.

## Проверка интерфейса

Проверяемый путь: процесс → агентный шаг → настройка локальной проверки → применение и публикация → повторное открытие → выполнение основного маршрута и сохранённое наблюдение.

**Browser plugin not available**: использован существующий Playwright workflow репозитория. Первый запуск остановился до открытия приложения из-за отсутствующего Chromium; установлен только закреплённый пакетом headless shell и FFmpeg, без изменения зависимостей проекта. Такой способ установки описан в [документации Playwright](https://playwright.dev/docs/browsers).

Используются собранный coordinator, настоящие process/run API, отдельная временная SQLite и Python worker в `--dry-run`. Подмена API-ответов в новых тестах отсутствует. Профиль имеет явную identity `test-only/browser-fixture`; MLX inference и предметное качество этот прогон не проверяет.

| Проверка | Что подтверждается |
|---|---|
| Unit → настоящий серверный normalizer | Все три типа, порядок, exact profile, `false`, `-0`, числовые пределы, дубли и ограничения текста |
| Boolean desktop/mobile | Ошибки неполного ввода, Escape/отмена, Tab и возврат фокуса, автосохранение, публикация/reload, сохранение параметров агента |
| Primary fallback desktop/mobile | Опубликованный процесс с shadow завершается обычным worker; реальный trace содержит `unavailable / disabled / primary` |
| Score/Choice desktop/mobile | Числа, изменение типа, перестановка/добавление/удаление вариантов, abstain, запрет дублей, публикация второй версии |
| Layout и console | Правильные URL/title, содержимое страницы, отсутствие error overlay, console warnings/errors и горизонтального переполнения; границы диалога внутри viewport |

Первый UI-прогон выявил зависимость подписи поля от содержимого вложенного control и наследование мелких стилей инспектора; исправлены явные связи ID и portal. Следующий прогон выявил неверное ожидание теста для кнопки второй публикации («Опубликовать» вместо существующей «Новая версия»). На мобильном снимке также исправлены отступы диалога. Визуальная перепроверка обнаружила устаревшие ошибки после исправления данных; после первой попытки применения ошибки теперь вычисляются из текущего ввода и исчезают сразу после исправления, включая перестановку вариантов. Неуспешные прогоны сохранены отдельно от финального результата.
