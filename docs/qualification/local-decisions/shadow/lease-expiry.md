# Shadow-наблюдение и истечение lease во время SQL-записи

Дата: **27.09.2026**. Проверен следующий gate после [preflight](./preflight.md): действительность lease при записи `decision.shadow`, включая ожидание блокировки PostgreSQL и идемпотентный повтор.

## Воспроизведённый дефект

Baseline `f7597b7095e25086b734004419168cebd1940f7c` проверял `lease_expires_at` в первом SELECT, передавая текущее время как параметр. PostgreSQL мог ждать блокировку дольше оставшегося срока lease. После снятия блокировки этот параметр оставался прежним. Между проверкой и COMMIT также могла задержаться запись события.

На PostgreSQL 17.6 настоящий собранный coordinator получал HTTP-запрос worker. Независимое соединение удерживало блокировку; тест дожидался подтверждённого `wait_event_type = 'Lock'` в `pg_stat_activity`, проверял ожидаемый SQL и только затем удерживал блокировку до expiry. Случайное истечение lease до начала запроса не засчитывалось.

| Граница | До исправления | После исправления |
|---|---|---|
| Ожидание `SELECT … FOR UPDATE OF s` | HTTP 200, новое наблюдение и событие сохранены после expiry | HTTP 400, новых наблюдений/событий 0/0 |
| Ожидание `INSERT INTO events` после UPDATE stage | HTTP 200, обе записи сохранены после expiry | HTTP 400, обе записи откатились |
| Повтор ранее сохранённого результата после ожидания stage lock | HTTP 200 для уже просроченного lease | HTTP 400; прежнее наблюдение и единственное событие сохранены |

Три SQLite-теста отдельно проверяют точную границу `now == expiresAt`: часы сдвигаются после **настоящего** SQL-чтения или INSERT. Baseline провалил все три проверки; после исправления они проходят. Восстановление после maintenance проверяет новый lease, отказ старому владельцу, сохранение ровно одного наблюдения и завершение primary с исходным ожидаемым выводом.

## Изменение и границы гарантии

`recordDecisionShadow` читает срок из уже заблокированной строки и проверяет его по свежему времени до возврата ранее записанного наблюдения. После записи observation и события выполняется ещё одна проверка. Исключение откатывает обе записи в существующей транзакции. Некорректная дата также отвергается. Протокол, схема БД, capability, модельный профиль и выбор primary не изменены.

Это проверка **до запроса COMMIT**, а не обещание, что физический COMMIT или HTTP-ответ всегда успеют до expiry. Она не решает скачки системного времени или рассинхронизацию часов между хостами. Сохранённое до expiry наблюдение не удаляется при позднем повторе.

[PostgreSQL Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html) описывает ожидание блокировки и работу с версией строки после её освобождения. Из этого для Агат следует необходимость повторно проверить время после ожидания. Замена параметра на `CURRENT_TIMESTAMP` не устранила бы весь интервал: [PostgreSQL фиксирует это значение на начале транзакции](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT). Проверка после последнего SQL-write соответствует уже проверенной [границе retrieval](../performance/retrieval-lease-write-fence.md).

## Проверка

```sh
node --import tsx --test apps/coordinator/test/local-decisions.test.ts \
  apps/coordinator/test/local-decisions-http.test.ts
bash scripts/test-fleet-ha-postgres.sh \
  --test-name-pattern='rejects shadow results when the lease expires|persists one shadow observation'
npm run test:coordinator
bash scripts/test-fleet-ha-postgres.sh
npm run typecheck
npm run docs:check
```

Целевые shadow/HTTP-тесты — **19/19**, PostgreSQL-гонки вместе с прежней проверкой двух экземпляров, restart и tenant RLS — **4/4**. Полная регрессия coordinator — **258/258**, typecheck всех workspaces — pass. Полный PostgreSQL-прогон — **31/31**; его логи и аудит документации зафиксированы в [протоколе с SHA и логами](./evidence/2026-09-27/shadow-lease-expiry/checks.json).

Две ошибки в самом тестовом стенде сохранены в evidence: повторяющееся имя процесса в общей PostgreSQL БД заменено уникальным; после проверки точного момента expiry SQLite-часы продвинуты на 1 мс, поскольку maintenance освобождает строго более старые lease. Первый docs-check обнаружил ещё не созданный evidence manifest; после завершения сборки evidence ссылки проверены повторно. Эти попытки не засчитаны как успешные проверки. Предметная модель здесь не запускается; ответ runtime явно тестовый. Это инженерная проверка хранения, без новой оценки качества MLX или production SLO.

Следующий gate — проверить действительность lease при подтверждении завершения primary. В текущем коде эта ветка использует отдельный SELECT; её правила времени нужно подтвердить независимо от shadow и retrieval, прежде чем менять поведение.
