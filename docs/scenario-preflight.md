# USE-002: готовность сценария процесса

Встроенный каталог в форме **Новый процесс**, вкладка **Готовность** редактора и диалог **Запустить процесс** используют общий серверный preflight. Проверка схемы остаётся отдельной проверкой структуры. Сохранение черновика не требует доступных workers или назначенных ролей.

## Состояния

API возвращает независимые признаки, а UI показывает каждый из них:

| Признак | Значение |
| --- | --- |
| `saved` — сохранено | В текущем проекте существует сохранённый процесс. Предпросмотр каталога ещё не сохранён. |
| `queueable` — можно в очередь | Закреплённая опубликованная версия и её конфигурация допустимы; runtime может принять запуск, есть место в очереди. |
| `runnableNow` — можно выполнить сейчас | Помимо допустимости очереди, сейчас есть подходящие свободные исполнители, полностью индексированные выбранные знания и доступные инструменты. |
| `scenarioVerified` — проверено на сценарии | Есть полный завершённый экземпляр с соответствующим fingerprint версии и конфигурации. Возвращается ссылка на подтверждающий запуск. |

Уже проверенный сценарий может временно не выполняться из-за занятого worker. Эти признаки не заменяют друг друга. Готовность сейчас не резервирует ресурсы и не гарантирует, что будущие этапы не будут ждать человека, таймера или сигнала.

## Проверки и восстановление

Каждый элемент `blockers` содержит стабильный `code`, `category`, причину, `blocks: queue | run` и `recovery: { label, href }`. Блокировка очереди также запрещает немедленный запуск. Блокировка выполнения позволяет **явно** выбрать «Поставить в очередь и ждать готовности».

| Проверка | Источник | Переход для исправления |
| --- | --- | --- |
| Версия, схема, назначения | Сохранённый draft либо точная immutable `process_versions` | Конкретный процесс, вкладка версии или шаг схемы |
| Runtime и команда | Runtime/profile агента, состав specialist team, heartbeat, свободные слоты, release/attestation/rollout и размещение проекта | Карточка runtime в Fleet, настройка конкретного агента либо подключение worker с указанным runtime/profile |
| Модели | Все модели агента и специалистов на одном worker; действующий model router | Карточка нужной модели / policy router |
| Знания | Только выбранные коллекции текущего проекта; наличие документов и всех embeddings нужной модели | Конкретная коллекция и её документы |
| Retrieval | Нужные embedding-модели на том же worker, который выполняет агента | Подключение worker с требуемой embedding-моделью |
| Required tools | Явные public names, включённый gateway/server, свежий каталог, доступность sandbox и NetworkPolicy для container, effective policy и emergency deny | Конкретный MCP-инструмент/сервер; для отсутствующего инструмента — его public name и подключение сервера |
| Scopes | Доступные credentials, срок, namespace, tool pattern и risk; scope HTTP-шага | Конкретные credentials или шаг процесса |
| Trigger | Manual; доступное неприостановленное расписание Temporal с next action; выбранный включённый start webhook данного процесса | Вкладка триггеров конкретного процесса |
| Квоты | Очередь проекта, размещение, project/global concurrency | Fleet проекта или выполняемые задачи |

Проверяются также закреплённые вложенные процессы. Scope secrets, webhook tokens и исходное содержимое знаний не включаются в ответ preflight. Согласование MCP само по себе не является blocker: `notices` сообщает необходимое число подтверждений, которые запрашиваются непосредственно при действии.

Переходы соблюдают существующий RBAC. Если раздел недоступен текущей роли, UI позволяет скопировать точную ссылку для администратора вместо перехода на запрещённую страницу. Настройку инфраструктуры выполняет администратор. Текущие шаблоны каталога не объявляют готовые внешние интеграции. Требования внешних инструментов объявляются через `graph.requiredTools`; они не выводятся из текста инструкции или названия роли.

[Пакет «Внутренний отчёт»](./internal-report-pack.md) использует тот же evaluator и контракт. `graph.requiredKnowledgeCollectionIds` закрепляет обязательные источники: они выбираются по умолчанию, а явное исключение блокирует очередь. `graph.mcpToolAllowlist: []` запрещает внешние MCP tools и при выдаче lease, и в gateway. Предпросмотр пакета использует будущие роли без записи в БД; после установки проверяется закреплённая версия реального процесса. Отсутствующая обязательная коллекция имеет переход к замене привязки и публикации новой версии.

## API

`POST /api/v1/process-templates/:id/preflight` принимает `catalogTemplateVersion`, `templateBindings`, необязательные `knowledgeCollectionIds` и `trigger`. Предпросмотр не создаёт процесс, run, embeddings или внешние вызовы. Устаревшая версия каталога даёт отдельный blocker с предложением обновить выбор.

`POST /api/v1/processes/:id/preflight`:

```json
{
  "version": 3,
  "knowledgeCollectionIds": ["collection-id"],
  "trigger": { "kind": "manual" }
}
```

`version` должен указывать существующую опубликованную версию. Без него готовность очереди не подтверждается. Trigger также может быть `{ "kind": "schedule" }` либо `{ "kind": "webhook", "webhookId": "id" }`. Чужой процесс возвращает `404`; чужой или удалённый выбранный источник — blocker без раскрытия его содержимого.

Для расписания проверяются знания из его сохранённой конфигурации; несовпадающий выбор источников даёт blocker с переходом к выбору. Start webhook сейчас не передаёт локальные знания, поэтому сценарий с выбранными коллекциями требует ручного запуска либо расписания.

Запуск из нового диалога передаёт тот же pin:

```json
{
  "input": "Проверить предоставленные факты",
  "version": 3,
  "startMode": "queue",
  "knowledgeCollectionIds": ["collection-id"],
  "resultDestination": "history"
}
```

`POST /api/v1/processes/:id/start` повторяет preflight в транзакции перед созданием экземпляра. `startMode: now` требует `runnableNow`; `queue` требует `queueable`. Несоответствие возвращает `409` с `{ error, preflight }`, без создания run. Публикация v4 после проверки v3 не подменяет запуск v3. Для старых клиентов без новых полей сохранён запуск в очередь последней опубликованной версии; новый UI всегда передаёт pin и режим явно.

Обязательные инструменты задаются в редакторе на вкладке **Готовность**, сохраняются в `graph.requiredTools` как массив `namespace__tool` и закрепляются при публикации. Они сохраняются при копировании шаблона и BPMN round trip через `agat:requiredTools`; изменение видно в version diff.

## Проверка при выполнении и доказательство

Preflight не выдаёт разрешение на будущий tool call. При выдаче lease scheduler снова проверяет worker/runtime/model/размещение, полноту выбранных знаний, поддержку retrieval и требования инструментов. MCP gateway сохраняет проверку policy, scopes и emergency deny непосредственно перед upstream-вызовом. Источник с неполными embeddings может ожидать в очереди, но процесс не получит agent lease до готовности.

При полном старте через API записывается `process.scenario.started` с fingerprint. Подтверждением считается только связанный экземпляр со статусом `completed`. Незавершённые, отменённые, отклонённые и failed экземпляры не подтверждают сценарий. Запуск с середины и replay не создают нового доказательства. Старые запуски без fingerprint также не объявляются проверенными задним числом.

Fingerprint связывает process/version, графы вложенных процессов, фактический trigger, определения агентов и команд, выбор/ревизии знаний, контракты инструментов, policy и ревизии credentials. Изменение этих данных требует нового полного запуска. Временная загрузка worker не стирает историческое доказательство. Это доказательство одного успешного прохождения конфигурации, а не оценка бизнес-качества каждого возможного входа или qualification всего solution pack. Manual evidence не доказывает доставку другим каналом: scheduled-start и start webhook записывают собственный trigger. Эти triggers используют последнюю опубликованную версию, поэтому preflight отклоняет несовпадающий pin. Сквозная эксплуатационная квалификация каналов остаётся в USE-006.

## Проверка изменений

```bash
node --import tsx --test apps/coordinator/test/scenario-preflight.test.ts apps/coordinator/test/scenario-preflight-http.test.ts
npm run test:web
npm run typecheck
```

Backend tests проверяют состояния, точный pin, очередь при недоступности runtime/model, состав команды на одном worker, источники/embeddings, scopes и их восстановление, sandbox, policy race, trigger readiness, project isolation, успешное прохождение согласования и отсутствие доказательства у частичного запуска. Frontend tests проверяют четыре состояния, доступность действий, ошибки, recovery URLs и вывод подтверждающего запуска. HTTP tests требуют локального loopback-порта.

Browser smoke-проверка на локальных fixtures покрывает выбор шаблона, переход к назначению роли, сохранение и публикацию, явную очередь с pin, переход к выбранной коллекции и trigger, ссылку на успешный запуск, delayed/stale ответы и retry после ошибки. Проверены desktop 1440×1000 и mobile 390×844; реальный Temporal и inference в этой проверке не используются.
