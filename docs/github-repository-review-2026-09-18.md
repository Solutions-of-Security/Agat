# Анализ представления Agat на GitHub

Дата проверки: **18 сентября 2026 года**. Репозиторий: [Solutions-of-Security/Agat](https://github.com/Solutions-of-Security/Agat). Опубликованная ветка `main` и локальный `HEAD` на момент начала анализа: [`5aec6d335b6f65f609361a068585572ac0e03ddf`](https://github.com/Solutions-of-Security/Agat/commit/5aec6d335b6f65f609361a068585572ac0e03ddf).

**Общая оценка: содержательный инженерный проект, которому нужно лучше показать продукт и оформить публичный цикл поставки.** У посетителя уже есть описание, быстрый запуск, лицензия и подробные руководства. Однако на главной странице он не видит интерфейс, готовый результат работы и опубликованную версию, которую можно выбрать для установки. Это затрудняет оценку проекта до скачивания.

Основания: просмотр публичной страницы в браузере, GitHub REST/GraphQL API, проверка файлов опубликованного среза, журнал последнего CI и проверка локальных ссылок документации. Репозиторий создан 17 сентября 2026 года; три публичных коммита, один участник и отсутствие stars/forks сейчас отражают возраст публикации. По этим числам нельзя оценивать качество продукта или его востребованность.

**1. Показать продукт и его пользу**

Текущая формулировка назначения понятна, но список технологий и возможностей ещё не демонстрирует, как работа выглядит для пользователя. Основные отличия, которые следует показать на одном конкретном примере: локальные модели, визуальный процесс, участие человека и прослеживаемый результат.

В репозитории уже есть [скриншот каталога агентов](./design/2026-09-workspace/agents-desktop.png) и [скриншот редактора процессов](./design/2026-09-workspace/process-editor-desktop.png). В [отчёте реализации](./design/2026-09-workspace/design.md) отдельно описаны фактические снимки и Imagegen-концепт. Для README следует выбрать или переснять актуальные экраны работающей версии, а концепты оставить обозначенными как концепты. Существующие снимки относятся к сентябрьским проверкам и требуют сверки перед использованием в новой поставке.

Рекомендуемый порядок README:

1. Название, короткое обещание результата, CI/license и статус публичной версии.
2. Один хорошо читаемый скриншот редактора или каталога; ссылка на демонстрацию длительностью около минуты.
3. Два-три практических сценария: обработка документа, поиск по базе знаний, процесс с согласованием. Для каждого — вход и наблюдаемый выход.
4. Один основной quickstart с проверенными требованиями и ожидаемым результатом.
5. Краткая таблица: доступно сразу / требует дополнительной настройки / в разработке.
6. Ссылки на документацию, Releases, roadmap и участие.

Вариант первой фразы: «Запускайте AI-агентов и визуальные процессы на своих моделях — с согласованиями и журналом выполнения».

Для первой демонстрации подходит цепочка «входной текст → агент → согласование → итоговый текст». Её нужно реально проверить на выбранной версии и сохранить вход, команды, конфигурацию модели и ожидаемый тип результата в `/docs`. Скриншот успешного запуска полезнее обещания неопределённого “production-ready”.

**3. Объяснить зрелость и версионирование**

GitHub не показывает опубликованных релизов, хотя [package.json](../package.json) содержит `1.7.0`, а [roadmap](./roadmap.md) описывает этапы 1.8 и 1.9. В roadmap уже аккуратно указано, что выполненные инкременты не означают выпуск версии и что production qualification остаётся отдельной проверкой. Эту короткую оговорку стоит вынести ближе к входной странице.

Необходима одна согласованная линия версий: публичный статус текущего среза, соответствующий package version, tag, release notes и правила обновления. Нельзя выводить стабильность релиза из одного номера `1.7.0`. Статус stable или prerelease следует выбрать по фактически пройденным критериям.

В первых release notes указать: поддерживаемые варианты запуска, известные ограничения, требуемые миграции, проверенные версии runtime и ссылку на CI. После появления проверенного release pipeline можно публиковать контейнерные образы с неизменяемыми tags/digests и provenance. Это отдельная задача поставки; присутствие Dockerfile само по себе её не закрывает.

**4. Защитить цикл изменений и уточнить Security policy**

По [API ветки](https://api.github.com/repos/Solutions-of-Security/Agat/branches/main) защита `main` отключена; [repository rulesets](https://api.github.com/repos/Solutions-of-Security/Agat/rulesets) отсутствуют. Успешный CI сейчас даёт сигнал о проверке, но обязательность этого сигнала перед изменением `main` не обеспечена правилами репозитория.

Разумный начальный набор: обязательный PR, успешный существующий check `test` из workflow `verify`, блокирование force push и удаления основной ветки. Review другого человека включать с учётом состава команды; при одном доступном сопровождающем сначала обеспечить выполнимый процесс и явные исключения. [CODEOWNERS можно хранить в `/docs`](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners), назначая реальные GitHub-команды или участников с соответствующим доступом.

[Security policy](./security.md) уже содержит подробные технические границы и не нуждается в создании дублирующего файла ради галочки. В её начало следует добавить порядок сообщения об уязвимости: какие версии поддерживаются, ссылку на [приватную форму GitHub](https://github.com/Solutions-of-Security/Agat/security/advisories/new), состав полезного отчёта и реалистичный порядок ответа. Приватный приём уже включён; нужно сделать его обнаружимым для человека. Срок ответа должен отражать возможности сопровождающих, а не быть выдуманным SLA. [Назначение Security policy в GitHub](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/add-security-policy).

**5. Сделать первое знакомство воспроизводимым**

[Основной quickstart](./README.md) использует порт 8787 и `qwen3:8b`. [Локальный Docker](./local-docker.md) начинается с порта 8788, занятого на машине автора порта 8787 и моделей из её `.env`. Документ явно описывает конкретный стенд, однако [оглавление](./index.md) предлагает его как общий путь установки. Этот переход легко принять за обязательную конфигурацию проекта.

Улучшение: начинать Docker-руководство с чистого клонирования, `.env.example`, генерации необходимых значений, выбранного профиля и проверки доступности. Порт должен выводиться из конфигурации или объясняться единообразно. Исторический протокол проверки оставить отдельным разделом либо документом в `/docs`.

Добавить один пример запроса, точные действия создания/выбора агента, ожидаемый статус запуска и место результата. Вместо неподтверждённых требований к памяти дать несколько фактически проверенных конфигураций с моделью, квантованием, объёмом контекста и железом. Текущую подсказку про зависимость памяти от модели сохранить. Зафиксировать рекомендованную версию Node.js для разработчиков; явно отличать проверенные CI-версии от минимально заявленных.

**7. Сделать границы CI видимыми**

В [журнале текущего CI](https://github.com/Solutions-of-Security/Agat/actions/runs/35278836208/job/105395821878) четыре набора явно отмечены `# SKIP`: S3-compatible Artifact Store, PostgreSQL Fleet/HA, region-loss DR PostgreSQL activation и SQLite → PostgreSQL migration. Они зависят от внешних сервисов и переменных окружения. Итоговый счётчик Node сообщает `skipped 0`, поэтому для определения покрытия здесь использовались строки отдельных suites, а не только сводная строка.

Существующие shell-скрипты уже дают основу для отдельных интеграционных jobs. Их можно запускать для релевантных изменений и перед релизом; проверки восстановления реальной инфраструктуры оформлять отдельным gate с сохранением результатов. Temporal history replay уже работает, но не подтверждает живое соединение с Temporal server и полный развёрнутый сценарий.

В ближайшую доработку CI включить:

- `npm run docs:processes:check` и проверку локальных Markdown-ссылок;
- проверку чистого старта минимального документированного профиля;
- один браузерный smoke: открыть приложение, создать/запустить сценарий, увидеть результат; текущие frontend-тесты проверяют в основном отдельные функции и контракты;
- отдельные jobs для существующих PostgreSQL/S3 интеграционных scripts;
- регулярные обновления зависимостей через Dependabot или аналог, с отдельным решением для npm, Python и GitHub Actions.

В репозитории нет `.github/dependabot.yml`. При этом dependency graph уже обновлялся, а история содержит исправление Dependabot alerts. Поэтому отсутствие файла конфигурации нельзя трактовать как отсутствие всей защиты зависимостей. Аналогично CodeQL работает через динамические workflows и уже включён.

Приложение отчёта в `docs/agent-process-priority-report` имеет собственные package.json, lockfile и тесты, но не входит в корневые `apps/*` workspaces и основной workflow. Следует явно решить, является ли оно поддерживаемой частью поставки. Если да — дать ему отдельные проверки; если это исторический исследовательский артефакт — обозначить статус и способ воспроизведения.

**8. Упростить навигацию по документации**

В проверяемом срезе 612 отслеживаемых файлов, из них 348 в `docs`; 236 относятся к приложению аналитического отчёта. Документация занимает около 23,4 MB, включая около 19,1 MB дизайн-материалов. Эти величины не создают сами по себе серьёзной проблемы размера репозитория, но объясняют, почему просмотр дерева `/docs` сложнее оглавления.

Сохранить [index.md](./index.md) главным навигатором. В нём различать пользовательские инструкции, справочник, эксплуатацию, решения по архитектуре и исторические исследования. В README достаточно короткой карты компонентов: `apps/coordinator` — API и оркестрация, `apps/web` — интерфейс, `apps/temporal-worker` — durable workflows, `workers` — выполнение задач, `edge` — мобильные клиенты. Подробности оставить в архитектурном руководстве.

Историю реализации и будущие планы полезно постепенно разделить на `docs/CHANGELOG.md` и roadmap: текущий roadmap занимает 683 строки. При этом его верхняя таблица статусов уже полезна, её стоит сохранить. Перемещение файлов выполнять вместе с обновлением ссылок; исправлять сейчас несуществующую проблему битых локальных ссылок не требуется.

**Практическая последовательность**

1. Первая итерация оформления: topics, Website, продуктовый скриншот, короткий блок статуса версии, ссылка на приватный канал уязвимостей. Это самые небольшие изменения с заметным эффектом для посетителя.
2. Первый воспроизводимый опыт: универсальный quickstart, входной пример и ожидаемый результат; проверка на чистом окружении, затем демонстрация и release notes.
3. Публичный процесс разработки: правила `main`, руководства участия, шаблоны и подготовленные issues.
4. Подтверждение поставки: проверки документации, браузерный smoke, интеграционные jobs, tag/release и при необходимости контейнерные артефакты.

Полная установка с нуля, LLM inference и инфраструктурные интеграции в рамках обзора не запускались. Результаты основных тестов взяты из CI указанного коммита; локально выполнены проверка ссылок и проверка каталога процессов.
